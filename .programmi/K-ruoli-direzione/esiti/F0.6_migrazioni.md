# F0.6 — Come si applica una migrazione in questo mandato (esito dell'indagine)

Data: 2026-09-14, sessione S1102. Tutto misurato sul repo e sul database vivo; nessuna cella «non trovato».

## 1. Il runner

`db/scripts/migrate.sh` (Windows: `db/scripts/migrate.ps1`, stessa semantica; `pnpm db:migrate`, `db:migrate:sh`, `db:migrate:vm` in `package.json:23-27`).

- Applica **tutta la catena** `db/migrations/*.sql` in **ordine lessicale** (`files=( "$MIG_DIR"/*.sql )`), in un solo flusso verso una sola `psql -v ON_ERROR_STOP=1`.
- Avvolge **ogni file** in `BEGIN; … COMMIT;` propri. 148 file su 411 contengono gia' `BEGIN;/COMMIT;` interni (misurato: `grep -l "^BEGIN;" db/migrations/*.sql | wc -l`): il doppio BEGIN produce solo un WARNING, e' la convenzione in uso, e V6 (`BEGIN; … COMMIT;` dentro il file) e' compatibile.
- Dopo il COMMIT di ogni file scrive il **registro** `sys.sys_schema_migrations(file_name, sha256, applied_at, applied_by, duration_ms)` con `ON CONFLICT (file_name) DO UPDATE`. Un file marcato in testa `-- @migrate: once` viene saltato se e' gia' registrato con la stessa impronta; `MIGRATE_FORCE_ALL=1` riesegue tutto; `MIGRATE_DRY_RUN=1` dice cosa farebbe.
- **Non esiste un modo per applicare UNA sola migrazione per nome.** La catena e' idempotente per costruzione e si riapplica intera: 411 file in ~17 s sulla VM.

## 2. Il registro

Esiste, e' pieno e coincide coi file: `select count(*), max(file_name) from sys.sys_schema_migrations` → `411 | 000414_…sql` (2026-09-14 14:55 UTC), contro 411 file in `db/migrations/`.

Query per sapere se una migrazione e' registrata (quella che `dove_siamo.py` esegue):

```sql
select applied_at, sha256 from sys.sys_schema_migrations where file_name = '000NNN_nome.sql';
```

## 3. La regola sui buchi

**Il runner NON rifiuta i buchi e NON controlla la contiguita' dei numeri**: applica cio' che trova, nell'ordine del nome. Ne discendono due regole del mandato, che sono disciplina nostra e non del runner: (a) un numero prenotato non si lascia mai vuoto (si chiude con una migrazione vuota `BEGIN; select 1; COMMIT; -- FINE 000NNN`); (b) il numero e' SEMPRE il successivo al massimo presente, mai un numero piu' basso inserito dopo — una migrazione con numero basso ma scritta tardi gira PRIMA di quelle che la seguono nel nome (e' il caso della 000210 auto-riparante che, fuori ordine, ha cancellato quattro permessi: memoria `selfhealing_migration_out_of_order_destroys`).

## 4. IL COMANDO ESATTO, in quest'ordine, per ogni migrazione del mandato K

1. `python ~/.claude/tools/guardiano.py` (V4).
2. Numero prenotato in `STATO.md` (`migrazione_prenotata`), committato, PRIMA di creare il file (V6).
3. Scrivere `db/migrations/000NNN_nome.sql`: `BEGIN; … COMMIT;`, idempotente, ultima riga `-- FINE 000NNN`.
4. Prova generale sul gemello, su copia usa-e-getta, DUE passate: il file va portato sul linux-pc prima del push con `scp db/migrations/000NNN_*.sql linux-pc:~/heuresys-advanced/db/migrations/` e poi `bash db/scripts/prova-idempotenza.sh` (→ `ci-rehearsal.sh`, ~26 s; esce ROSSO se il gemello non risponde o ha un numero diverso di file, e non ripiega mai su questa macchina). Precondizione misurata: linux-pc e VM rispondono via ssh ed erano entrambi a `a4d70ba2` (fanno `git pull` solo quando glielo si chiede).
5. Snapshot (V6): `bash .programmi/K-ruoli-direzione/tools/pg_dump_pre_k.sh <voce>` → sulla VM, `pg_dump -Fc` (~138 MB, misurato sugli snapshot pre-deploy del 14/09) in `pg_dump_snapshots/pre-K-<voce>_<sha7>_<ts>.dump` (cartella gitignored; il linux-pc la tira giu' di notte). Esce rosso se il file manca o e' vuoto.
6. Commit del file di migrazione (`git add` + `git commit -F … -- <path>`) e push.
7. **Applicazione: `pnpm db:migrate:vm`** (→ `db/scripts/migrate-on-vm.sh`: `git pull --ff-only` sulla VM e poi `migrate.sh` sull'intera catena, ~17 s). Con `--no-pull` si prova un file portato con `scp` prima del push; non e' la via normale.
8. Post-condizione: `python .programmi/K-ruoli-direzione/tools/dove_siamo.py` → la riga della voce dice `completo · registrata <ora> · effetto PRESENTE`. La query dell'EFFETTO e' quella del dizionario `EFFETTI`, per voce.

Da Windows via tunnel (`pnpm db:migrate` / `db:migrate:sh`) la stessa catena costa ~80 minuti (misura del 2026-08-27): resta possibile, non e' la via.

## 5. Due vincoli che le migrazioni del mandato devono rispettare, misurati qui

- **Ogni vista `sys.v_*` nuova diventa una sentinella di `db_health.py`** (raccoglie tutte le viste dello schema e pretende zero righe, salvo `INFORMATIVE`): una vista di prova o una sentinella «nasce rossa» va dichiarata, oppure deve restituire zero righe.
- **La catena si riapplica intera a ogni deploy** (ADR-0035): una migrazione che crea un oggetto e una successiva che lo ritira devono convergere anche alla seconda passata. Il file che CREA deve saper riconoscere il ritiro (non ricreare cio' che e' stato ritirato) e il file che RITIRA deve essere un no-op se il ritiro c'e' gia'. E' esattamente cio' che la simulazione 3.5 (F0.4) deve provare con 000415/000416.
