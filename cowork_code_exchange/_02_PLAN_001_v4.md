## §-1 — Audit trail of corrections (for next-supervisor handoff)

This PLAN has been amended four times. The trajectory matters because the **MIGRATION_STATUS_2026-05-18.md Phase 1 report — the original oracle for the entire migration plan — contained two inferential errors** that propagated through v1, v2, v3, and v3-bis:

1. **§10 E10-4 of MIGRATION_STATUS asserted**: "the COMPLETE state lives in the engine's in-memory state machine, not in the durable `brownfield.import_runs.import_run_status` column."

   **Reality (per CLI evidence E2 + E3)**: the engine writes to `audit.import_validation_results` and `audit.import_approval_decisions` correctly. The 0 counts observed in Phase 1 were artifacts of `afterAll` cleanup in `apps/api/test/brownfield-wave-executor.integration.test.ts:45-59`, which DELETEs rows post-test by `runId`. Phase 1 forensic counting was code-blind: it counted rows without inspecting what the code does at run-time.

2. **§8.A high #3 of MIGRATION_STATUS asserted**: "All 52 lineage rows have `source_lineage_import_run_id = NULL` — the executor never back-populates the FK."

   **Reality (per CLI evidence E1 + E5)**: `batchWriteLineage` (engine.ts lines 947-998) correctly populates `source_lineage_import_run_id` on both INSERT and `ON CONFLICT DO UPDATE` paths. The 52 NULL rows are historical: the FK has `ON DELETE SET NULL` (confdeltype='n'), so prior import_runs rows that were DELETEd cascaded SET NULL on the lineage records they had emitted.

**Lesson for next supervisor**: Phase-1 DB-only forensic analysis is **insufficient on its own** to declare gaps in audit/lineage machinery. Code reading is mandatory to distinguish "engine doesn't write" from "rows existed and were cleaned up" or from "rows existed and FK action nulled them." When the next Goal in this stream (001b, then 002+) requires similar gap analysis, the executor's first 2-3 turns should always be code inspection of the relevant function, never just DB count comparison.

### §2.4 — Transform compiler design (unchanged from v3-bis §2.4 except for added rejection of 8 extra transforms.ts codes)

12 mechanical codes mapped to SQL fragments, all via `pg-format` `%I` / `%L`:

```
DIRECT_COPY:        format('%I', src_col)
CAST_TIMESTAMPTZ:   format('CAST(%I AS TIMESTAMPTZ)', src_col)
CAST_INT:           format('CAST(%I AS INTEGER)', src_col)
CAST_VARCHAR:       format('CAST(%I AS VARCHAR)', src_col)
CAST_BOOLEAN:       format('CAST(%I AS BOOLEAN)', src_col)
CAST_NUMERIC:       format('CAST(%I AS NUMERIC)', src_col)
TRIM:               format('TRIM(%I)', src_col)
UPPERCASE:          format('UPPER(%I)', src_col)
LOWERCASE:          format('LOWER(%I)', src_col)
CONSTANT:           format('%L', payload.value)
SKIP:               (no SQL fragment; column omitted from SELECT list)
LOOKUP_FK:          format('(SELECT %I FROM %I.%I WHERE %I = %I)', 
                           target_pk_col, target_schema, target_table, lookup_col, src_col)
                    [LOOKUP_FK payload semantics per CLI evidence at turn 7: {match_on: "<source_col>", target_table: "sys_xxx"}.
                     Convention-based — lookup_col derived from naming convention, return col is target_pk_col.]
```

Unsupported (8 extra from transforms.ts) + (JSON_EXTRACT, LINEAGE_SOURCE_NK) = throw `UnsupportedTransformError(code, mapping_id)` at compile time. The executor catches and records the SKIPPED row in `audit.import_validation_results`.

Injection-safety unchanged from v3-bis §2.4. Test in §2.2 item 7.
