## §2.2 — Code change plan (Items A–L, ordered by dependency)

Each Item: file(s), current state, intended change, risk class, test coverage, atomic commit.

### Item A — `transform-compiler.ts` + `upsert-sql.ts`: LOOKUP_FK `legacy_<X>_id` jsonb-lookup convention (Problem 1)

- **Files**: `apps/api/src/modules/brownfield-wave-executor/transform-compiler.ts`, `apps/api/test/transform-compiler.test.ts`.
- **Current state (Goal 002 v1)**: LOOKUP_FK case reads `payload.match_on` literally; if `match_on` references a non-existent column, runtime SQL fails with `column "legacy_tenant_id" does not exist`.
- **Intended change**:
  1. Extend whitelist regex from Goal 002 §2.4.1 to recognize a third form: `^legacy_([a-z_]+)_id$` (capture group 1 = entity name).
  2. When the third form matches AND target_table schema has a `<entity_name>_metadata` jsonb column, emit SQL: `t.<entity>_metadata->>'legacy_id' = staging.staging_raw_record->>'<original_source_column>'`. The "original_source_column" comes from `column_mapping_source_column_name` for the originating mapping.
  3. Fallback (no `<entity>_metadata` column OR EXEC step 0 verified `legacy_id` key absent from any sample): emit SQL using `brownfield.tenant_id_mappings.legacy_id` JOIN (Item D); for `legacy_user_id`, analog `brownfield.user_id_mappings` is OUT-OF-SCOPE — instead, lookup via `staging_raw_record->>'user_email'` against `sys.sys_users.user_email` (deterministic).
  4. Compiler emits a structured `auditClassification` field on `CompileResult` so engine.ts records `LOOKUP_FK_CONVENTION=JSONB_LEGACY_ID` vs `LOOKUP_FK_CONVENTION=LITERAL_COL` per mapping (audit transparency).
- **Risk class**: medium. Whitelist regex protects injection; sample-based EXEC step 0 prevents convention misapplication.
- **Test coverage** (added to `transform-compiler.test.ts`):
  - happy: `match_on=legacy_tenant_id` + target=`sys_tenancies` (has `tenant_metadata`) → emits jsonb lookup
  - happy: `match_on=legacy_user_id` + target=`sys_users` → emits jsonb lookup
  - happy: `match_on=skill_name` (literal form, regression) → emits literal column
  - happy: `match_on=learning_module_metadata->>'legacy_id'` (expression form, regression) → unchanged
  - adversarial 1: `match_on=legacy_tenant_id; DROP TABLE--` → InvalidLookupFkPayloadError
  - adversarial 2: `match_on=legacy_'X'_id` → InvalidLookupFkPayloadError (quote in entity name)
  - adversarial 3: `match_on=legacy_NOSUCH_id` + target has no `nosuch_metadata` → fallback path or audit-emit error per §2.4
  - **5 adversarial fixtures minimum** (per A2-W1).
- **Atomic commit**: `feat(api): MVP-3 Tappa D — LOOKUP_FK jsonb-legacy-id convention (Goal 003 Item A)`.

### Item B — `transform-compiler.ts` + `upsert-sql.ts`: CAST_* generalize for type-coerce auto-wrap (Problem 3)

- **Files**: `apps/api/src/modules/brownfield-wave-executor/upsert-sql.ts` (CAST_MAP table) + `transform-compiler.ts` (registry of `CAST_*` transforms).
- **Current state**: Auto-wrap matrix Goal 002 v1 supports `DIRECT_COPY`/`TRIM` × {12 target types}. CAST_INT path bypasses this (already emits `::int`-cast in compileTransform), but the wrapper at upsert-sql doesn't detect CAST already applied → for `smallint` target, `::int` cast emits, then implicit cast to `smallint` may fail if value exceeds smallint range.
- **Intended change**:
  1. Add `CAST_SMALLINT` transform code in transform-compiler (emits explicit `::smallint`).
  2. Update `column_mapping_transform_payload` for the 2 affected mappings (REPORT 002 §3.5 `learning_path_step_ordinal`) to use `CAST_SMALLINT` instead of `CAST_INT`. **NOTE**: this is a `brownfield.column_mappings` UPDATE on wave=1 rows — see §2.10 advisory A1 (this conflicts with PROMPT §4.2 "no UPDATE wave=1 rows"; flagged for Cowork clarification).
  3. Alternative if §2.10 A1 resolves to "no UPDATE wave=1": extend Goal 002 Item E auto-wrap to detect `CAST_INT` → check target column type → if `smallint`, emit `::smallint` instead of `::int`. **Recommended** (no DB write).
- **Risk class**: low. Type-coerce purely SELECT-list side; no FK or upsert key impact.
- **Test coverage**: 3 tests in transform-compiler.test.ts (smallint auto-wrap, regression CAST_INT untouched, regression DIRECT_COPY untouched).
- **Atomic commit**: `feat(api): MVP-3 Tappa D — CAST_* auto-wrap generalization (Goal 003 Item B)`.

## §2.4 — Injection safety design

Goal 003 extends the Goal 002 injection safety surface to cover:

### 2.4.1 — LOOKUP_FK 3rd form whitelist (`legacy_<X>_id` → jsonb-lookup)

- Whitelist regex: `^legacy_([a-z_][a-z0-9_]*)_id$` (group 1 = entity, `[a-z_][a-z0-9_]*` excludes uppercase, digits-as-leading, quotes, semicolons, dashes).
- Entity name passes through `format("%I", entity || '_metadata')` for the column reference and through a separate `format("%L", 'legacy_id')` for the literal jsonb key.
- Original source column name (e.g., `legacy_tenant_id` in `staging_raw_record`) escaped via `format("%L", source_col)`.
- All 3 forms tested in adversarial fixtures (Item A test coverage).

### 2.4.2 — Wave 2/3/4 dynamic mapping payload validation

Every new mapping payload passes through:
1. **Static check**: `column_mapping_target_column` is a literal valid SQL identifier (regex `^[a-z_][a-z0-9_]*$`).
2. **Schema check** (U-2026-05-19-01): LEFT JOIN `information_schema.columns` to confirm the column exists OR is the `<entity>_metadata->>'legacy_id'` jsonb-lookup convention.
3. **Transform code whitelist**: only the 14 supported transform codes; unknown → INSERT rejected.
4. **PII column-name regex** (Wave 3 only): excludes columns matching PII pattern at authoring time (Item G).
5. **§2.12 CP2 SQL function** `brownfield.validate_lookup_fk_payload()`: enforced via INSERT trigger on `brownfield.column_mappings` (deferred to Item F migration 000034 as a piggyback if CP2 accepted).

### 2.4.3 — Wave 4 numeric range validation

`sys.sys_talent_scores.score_value` must be in [0, 1]. Enforced via CHECK constraint on the target column (if not already present) OR at mapping-authoring time via CHECK validation in the SQL fragment.

### 2.4.4 — Compensation amount filtering (Wave 4)

Authoring-time regex EXCLUDE on column_mapping_target_column matching `^compensation_amount_(min|max|.*)$` for `sys.sys_position_compensation_profiles` target table. Asserted in Item I test coverage.

## §2.12 — Counter-proposals (executor strategic input)

These are SHIPPING-ACCELERATION proposals beyond strict PROMPT 003 §2.2 Items. They reduce EXEC cycle count and increase robustness. **Per Enzo direttiva "fai le tue obiezioni nel plan e eventuali proposte"**.

### CP1 — Mapping-discovery helper script (`scripts/brownfield/discover-wave-mappings.mjs`)

**Problem**: Items E + G + I require manually authoring ~188 mapping rows (~80 + 50 + 58). At ~5 min per mapping (read source schema, identify target, build payload, U-cross-check) = ~15h pure authoring time = ~30+ executor turns minimum.

**Counter-proposal**: build a Node.js helper script that:
1. Reads `legacy_mirror.<table>` schema via PG introspection.
2. Cross-references with `docs/brownfield/BROWNFIELD_ADAPTATION_MAP.md` (574-line canonical map) for target sys.* table.
3. Generates a DRAFT `(table_mapping, column_mappings[])` spec in JSON/SQL per source table.
4. Runs U-2026-05-19-01 cross-check on the draft + flags INVALID rows.
5. Outputs to `db/seeds/brownfield/wave<N>/_draft_<table>.sql` for human review.

CLI reviews draft + commits final SQL seed file per source-table batch (≤10 source tables/turn vs 1/turn manual).

**Savings**: ~10 turns across Items E/G/I (from ~26 to ~16 turns).
**Risk**: CP1 helper may misidentify targets → fallback is human review (always required).
**Recommendation**: **STRONGLY RECOMMENDED**. Without CP1, the 79-turn budget likely overruns to ~87.

**Cowork decision needed**: accept CP1?

### CP2 — `brownfield.validate_lookup_fk_payload()` SQL function + INSERT trigger

**Counter-proposal**: add SQL function in migration 000033 (or piggyback in 000034):

```sql
CREATE OR REPLACE FUNCTION brownfield.validate_lookup_fk_payload(
  p_target_table varchar, p_match_on varchar

CREATE TRIGGER brownfield_column_mappings_lookup_fk_validate
  BEFORE INSERT ON brownfield.column_mappings

```

**Effect**: the gate is enforced at DB level for ALL future LOOKUP_FK mappings, regardless of authoring path. Goal 003 closure benefits + future Goals (004+, if Cowork decides) benefit too.
**Risk**: trigger adds ~5ms overhead per INSERT (R10 in §2.8); negligible at registry scale (~188 INSERTs total).
