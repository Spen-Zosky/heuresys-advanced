## 1. Legacy Source Overview

The legacy export is a **PostgreSQL 16** dump of the production `heuresys_platform` database (the prior generation of the platform, source: `heuresys_platform@oracle-vm-default:5432`). Key facts from the export's own `README.md`:

| Metric | Value |
|--------|------:|
| Business tables catalogued | **576** |
| Total tables (incl. excluded) | 582 |
| Tenant‑scoped tables | 335 |
| Foreign keys | 950 |
| Active RLS policies | 376 |
| Views | 110 |
| Materialized views | 6 |
| Lexicon domains | 16 (+ uncategorized) |
| Tenants in legacy data | 4 (Heuresys System, RTL Bank, SmartFood, EcoNova) |
| Total employees across 4 tenants | **270** (RTL Bank 158 · SmartFood 82 · EcoNova 26 · Heuresys System 4) |
| Total users (auth identities) | **274** (270 with `employee_id` + 4 platform users, 2 with `employee_id IS NULL`) |
| Data nature | **Demo data** generated by the platform owner — no real PII; anonymization not required, only `user_is_synthetic = true` tagging |

> **Native target tables not derived from brownfield (ADR‑0011 ESS additions).** A few canonical tables introduced by the new architecture have **no legacy counterpart** and are created from scratch by migrations:
>
> - `sys.sys_inbox_notifications` (migration 000027 — ESS inbox)
> - `audit.user_self_service_actions` (migration 000027 — ESS audit trail)
> - `sys.sys_user_target_positions` (migration 000018 career_succession — used by ESS "Request career target" CTA)
>
> These tables are populated at runtime by the new platform (not via brownfield import). They are listed in `TARGET_SCHEMA_DESIGN.md` §1.5 / §9 / §13.1 respectively and do not appear in the per‑domain adaptation map below.

The legacy export already documents **7 pre‑excluded tables** in `exclusions.md`: `_prisma_migrations`, `account`, `audit_logs`, `kg_edges`, `kg_nodes`, `session`, `verification_token`. We honor those exclusions and add many more under our stricter canonical policy.

The legacy export already excludes (`exclusions.md`): `_prisma_migrations`, `account`, `audit_logs`, `kg_edges`, `kg_nodes`, `session`, `verification_token`. All seven are honored: never imported.

### 5.3 RLS / multi‑tenant infrastructure

The legacy DB enables **376 active RLS policies**. Per ADR‑0004 + I5 the new platform uses **API‑level tenant filtering, never RLS**. No `.meta-rls.json` entry is imported. RLS metadata is preserved only inside `brownfield.source_tables.legacy_rls_policy` JSONB for traceability — never executed.

### 5.4 Foreign keys to excluded tables

950 legacy FKs total. FKs whose target is excluded are recorded in `brownfield.source_columns.legacy_fk_target_excluded = true`. The transformation logic drops or rewrites those FKs to the canonical equivalent in `sys.sys_*`.

## 9. Refresh Procedure

If a new `db-export.zip` arrives, a **commit + PR is mandatory** for full traceability. No auto‑update in CI: every refresh leaves a reviewable diff on the canonical adaptation map and exclusion report.

### 9.1 Sequenza operativa (mandatory)

1. **Branch**: open `git checkout -b brownfield-refresh-YYYY-MM-DD`.
2. **Replace input zip**: commit the new `docs/source_bundle/brownfield/db-export.zip` (preserves the old zip via git history).
3. **Re‑run the inspection chain** (Tasks 3–6 of the execution sequence): extract → `inspect_db_export.py` → `classify_brownfield_tables.py` → `_classify_with_domains.py` → fresh CSV.
4. **Snapshot the previous CSV** to `qa_artifacts/brownfield/tables_with_domains.<prev_date>.csv` (the live `_inspection_artifacts/tables_with_domains.csv` is gitignored; the snapshot in `qa_artifacts/` is **committed** to provide a diff anchor across refreshes).
5. **Diff** the new CSV against the snapshot (`diff qa_artifacts/brownfield/tables_with_domains.<prev_date>.csv docs/brownfield/_inspection_artifacts/tables_with_domains.csv`). Save the diff to `qa_artifacts/brownfield/refresh_diff.<new_date>.txt`.
6. **Curate this map** (§§ 4 + 6): for each table appearing only in the new CSV, add a row honoring the existing classification logic; for each table whose `comment`, `rls_enabled`, or `domains` changed, re‑evaluate classification.
7. **Re‑review `BROWNFIELD_EXCLUSION_REPORT.md`** for any new sensitive fields surfaced by the refresh (column comments may have changed).
8. **Re‑review `BROWNFIELD_TABLE_CLASSIFICATION_REPORT.md`** §3 (per‑domain rationale) and §4 (edge cases) for impact.
9. **Update sizing & totals**: verify §3 totals (576 ± Δ); update §1 if tenant/employee counts changed.
10. **Open PR** named `[BROWNFIELD] Refresh YYYY-MM-DD — N tables added, M removed, K reclassified`. The PR description **must** include:
    - the diff stats (added/removed/reclassified tables, by domain);
    - a flag for any tables whose classification changed from non‑EXCLUDE to EXCLUDE (privacy/scope review);
    - a flag for any tables whose classification changed from EXCLUDE to IMPORT/TRANSFORM (sensitive‑review list update);
    - link to the snapshot CSV + diff file.
11. **Review & merge**: PI signs off. Auto‑merge is not allowed for brownfield refreshes (R12 bus factor mitigation: every refresh is a reviewable artifact).
12. **Post‑merge**: re‑run any pending brownfield wave only if the refresh introduced new IMPORT/TRANSFORM rows for that wave.

### 9.2 What is NOT allowed

- **No silent re‑run of the inspection chain** that mutates `docs/brownfield/_inspection_artifacts/*` without a corresponding PR.
- **No direct edit of this `BROWNFIELD_ADAPTATION_MAP.md` without re‑running the inspection chain** (the doc must reflect the actual CSV state, not a stale copy).
- **No CI job** that overrides this document automatically. Refresh is a deliberate, human‑approved act.

### 9.3 Cadence expectation

Brownfield refresh is **not** a periodic activity. It is triggered only when the legacy `heuresys_platform` schema or data evolves meaningfully (e.g. a domain re‑modeled, a new tenant onboarded, a new module shipped in the legacy app). Expected cadence: < 4 times per year.
