### Stato architettura RSC vs client — l'UNICA decisione aperta (F-WS-D-1)

Verifica live su HEAD (read-only):

| Metrica | Valore (WS-D baseline) | Riverifica HEAD |
|---|---|---|
| File `"use client"` (`apps/web/src`) | 78/101 `.tsx` | **78** (invariato) |
| `(authenticated)` page/layout client-side | 65/66 (unico RSC = `system-health/layout.tsx` gating) | invariato |
| `Suspense` / `React.lazy` | 0 / 0 | **0** |
| `loading.tsx` / `error.tsx` co-locati | 0 / 0 | **0** |
| Server Action / RSC-fetch / fetch server-side | 0 / 0 / 0 | invariato |

- **Ogni pagina business è un client component** che fa data-fetch via TanStack Query nel browser (`lib/api/*` + 65 `useQuery`). Nessun Server Component fa il fetch; nessun dato è nell'HTML iniziale.
- Conseguenza misurata: il **first-meaningful-paint = idratazione + N round-trip `/api`** (seriali/paralleli) invece di streaming RSC server-side; ogni pagina ri-implementa loading/error in-component (`data-table-panel.tsx:72-97`) invece di usare boundary RSC.
- **Razionale architetturale presente in repo (non è negligenza)**: la SPA-in-App-Router è allineata 1:1 al cookie-auth model + silent-refresh client-side (D-26). Un RSC-fetch dovrebbe inoltrare i cookie HttpOnly `hrx_access`/`hrx_refresh` server→server verso `/v1/*` (oggi `proxy.ts` e `apiFetch` vivono lato client); il `proxy.ts` (rename Next del `middleware`) passa su presenza di `hrx_access` **O** `hrx_refresh` (sessione resumable, F-WS-D-8). Spostare il fetch sul server tocca **come e dove l'access-token viene mintato/inoltrato** → impatta il security model, per questo è DOSSIER e non quick-win.

## Opzioni

> Pre-condizione **verify-first** comune a tutte (F-WS-D-1 lo impone esplicitamente): prima di stimare il guadagno, misurare TTFB/LCP reale (Lighthouse / `@next/bundle-analyzer`) su 2-3 pagine liste rappresentative (es. una `analytics/*`, una lista admin, una `/me/*`). Senza baseline perf reale, qualsiasi stima del payoff è impressione (vietata, AUDIT_PROTOCOL §1).

### Conservativa — "Resta client-side, aggiungi boundary UX (loading/error/Suspense) senza toccare l'auth"

- **Scope**: nessun cambio al data-fetch model. Si aggiungono `loading.tsx` + `error.tsx` per-route (almeno sulle famiglie liste/detail più pesanti) e qualche `Suspense` boundary, così il first-paint mostra uno skeleton/spinner servito dall'RSC shell mentre il client idrata e fa fetch. Si rimuove la duplicazione del loading/error in-component (`data-table-panel.tsx:72-97`) a favore dei boundary nativi. L'access-token resta mintato/inoltrato lato client come oggi.
- **Impatto**: UX percepita↑ (first-paint con skeleton invece di blank+idratazione) · DX↑ (un boundary per-route invece di N re-implementazioni in-component) · perf reale **neutra** (il dato arriva sempre dal client; migliora la *percezione*, non il TTFB del dato) · security **neutro** (auth model invariato — leva chiave: zero rischio sul path D-26).
- **Costo**: ~1 sessione (additivo, per-route, nessun refactor del fetch; gate = E2E Playwright prod verdi + nessuna regressione visiva).
- **Rischio**: **basso**. Solo file additivi (`loading.tsx`/`error.tsx`), nessun cambio di contratto né del path auth; coperto dagli E2E prod esistenti.
- **Reversibilità**: alta (i boundary sono file isolati, removibili).
- **Prerequisiti**: nessuno.

### Evolutiva — "RSC-fetch sulle sole pagine read-mostly non-mutanti, con cookie-forwarding server→server"

- **Scope**: si convertono a Server Component (con fetch server-side) **solo** le pagine read-mostly non-mutanti — liste e detail in lettura (`analytics/*` read, viste catalogo/detail, dashboard read-only) — introducendo un layer di forwarding dei cookie HttpOnly `hrx_access`/`hrx_refresh` da Next-server verso `/v1/*` (richiede che l'API accetti l'access-cookie da un server-fetch e che il forwarding gestisca il refresh server-side o deleghi al client il primo refresh). Le pagine **mutanti** (form, azioni CRUD, ESS write) restano client component con `apiFetch` + TanStack Query come oggi. Si abbinano i boundary RSC (loading/error/streaming) della Conservativa.
- **Impatto**: perf reale↑ (dato nell'HTML iniziale per le read-page → TTFB/LCP migliori, niente N round-trip post-idratazione su quelle pagine) · UX↑ (streaming RSC) · DX neutro/misto (due idiomi: RSC-fetch read + client-fetch write) · **security: superficie nuova** (il forwarding del cookie HttpOnly server→server e l'eventuale refresh server-side sono un nuovo punto del path auth — va progettato per NON regredire il single-flight + Web Lock cross-tab di D-26, che vivono client-side).
- **Costo**: ~2-3 sessioni (design del cookie-forwarding + refresh server-side, migrazione a ondate per famiglia di pagine, nuovi E2E che coprano il path RSC-fetch).
- **Rischio**: **medio**. Il rischio non è perf (è il payoff) ma **auth**: il refresh single-use con replay-detection è progettato attorno al client (`navigator.locks` cross-tab). Un fetch server-side che incontra un 401 deve coordinarsi con il refresh client senza doppia-rotazione (replay → hard-logout dell'intera family). Mitigazione: convertire **solo** read-page (nessuna mutazione server-side), lasciare il refresh al client (RSC legge col cookie corrente, se scaduto la pagina degrada al client-fetch), rollout incrementale per-famiglia con gate E2E auth dedicato.
- **Reversibilità**: media (una pagina RSC-converted torna client component, ma il layer di cookie-forwarding è un punto centrale da disfare).
- **Prerequisiti**: Conservativa (boundary) prima; baseline perf reale (verify-first) che dimostri il guadagno TTFB/LCP atteso; design esplicito del cookie-forwarding revisionato contro D-26 (cross-ref WS-H); conferma che `/v1/*` accetta l'access-cookie da un server-fetch Next.

### Radicale — "Fetch-on-server universale: tutte le pagine RSC con session-forwarding centralizzato"

- **Scope**: si ri-architetta l'intera app `(authenticated)` a fetch-on-server: un layer centrale di session/cookie-forwarding inoltra l'identità verso `/v1/*` per ogni pagina, RSC ovunque possibile, Server Actions per le mutazioni, client component ridotti ai soli widget interattivi (chart `ssr:false`, form controllati). Riscrive di fatto il modello di idratazione e sposta il baricentro del fetch dal browser al Next-server.
- **Impatto**: perf reale↑↑ (tutto streaming server-side, minimo JS al client, niente waterfall di idratazione) · UX↑↑ · DX↓ inizialmente (un solo idioma RSC ma riscrittura ampia) · **security: ridisegno del path auth** (il silent-refresh client-side D-26 va sostituito o duplicato server-side; le Server Actions per le mutazioni reintroducono CSRF/replay da gestire nel nuovo modello).
- **Costo**: ~4+ sessioni (riscrittura di 64 pagine authenticated + nuovo session model + Server Actions + riscrittura suite E2E + nuovo/aggiornato ADR sul security model).
- **Rischio**: **alto**. Tocca direttamente l'invariante più collaudato e recentemente hardened del progetto (D-26 silent-refresh + replay-detection + Web Lock cross-tab). Un ridisegno del session model è la classe di cambiamento con il più alto blast-radius su auth; i 65 `useQuery` e il pattern client-side sono profondamente cablati. Reward perf reale, ma reintroduce superficie di sicurezza appena chiusa.
- **Reversibilità**: bassa (riscrittura architetturale ampia, non un revert di commit).
- **Prerequisiti**: nuovo ADR sul session/auth model server-side; baseline perf che giustifichi l'effort; budget multi-sessione esplicito; ri-conferma che il guadagno vale la riapertura del path auth.

## Raccomandazione motivata

**Conservativa subito (GO, ~1 sessione, rischio basso); Evolutiva solo dopo una baseline perf reale che dimostri il guadagno (verify-first), e solo sulle read-page; Radicale sconsigliata (DEFER/WON'T).**

Razionale evidence-based:

1. **La leva quick-win di D-04 è già incassata** — il chart code-split (F-WS-D-4, l'unico HIGH *azionabile meccanicamente*) è chiuso (QW-D1/D2 applicati al repo). Ciò che resta è un **trade-off architetturale cosciente** (F-WS-D-1), non un difetto: il frontend client-side è coerente con un auth model pulito e collaudato. Non c'è leva di *correttezza/sicurezza* che forzi il cambio.
2. **La Conservativa è quasi-gratis e a rischio nullo sul path auth**: i boundary `loading.tsx`/`error.tsx`/`Suspense` migliorano il first-paint *percepito* e ritirano la duplicazione loading/error in-component, **senza toccare il fetch model né D-26**. È il miglior rapporto valore/rischio e va fatta comunque.
3. **L'Evolutiva è il vero payoff di perf *reale*** (dato nell'HTML iniziale → TTFB/LCP migliori) ma il suo rischio è interamente **auth-side**: il cookie-forwarding server→server e il coordinamento col refresh single-use/replay-detection di D-26 sono la parte delicata. Va fatta **solo** (a) dopo una baseline Lighthouse che quantifichi il guadagno (F-WS-D-1 lo impone: *"misurare TTFB/LCP reale prima di stimare"*), (b) **solo sulle read-page non-mutanti** lasciando il refresh al client, (c) a ondate con gate E2E auth dedicato. Non è bloccante: il pattern attuale funziona e performa accettabilmente per una SPA admin interna.
4. **La Radicale è sconsigliata**: riscrive il session model e reintroduce superficie di sicurezza (CSRF/replay nelle Server Actions, refresh server-side) appena chiusa con D-26, per un reward perf che l'Evolutiva ottiene in larga parte sulle sole read-page senza riaprire il path auth dell'intera app. Il blast-radius su auth non è giustificato dai findings (nessun finding segnala il client-side fetch come *problema*, solo come *opportunità*).

**Bonus a costo zero (parte della Conservativa)**: ora che `optimizePackageImports` è attivo (QW-D2) e i chart sono code-split (QW-D1), una **misura `@next/bundle-analyzer` prima/dopo** confermerebbe che echarts/three sono fuori dal chunk iniziale delle analytics-page — chiude il loop "verify-first" che WS-D lasciava aperto (la quantificazione KB richiedeva un build, non eseguito in fase A).

## Cosa decide l'utente

1. **Go/defer/won't sulla Conservativa** (boundary `loading.tsx`/`error.tsx`/`Suspense` per-route + de-duplicazione loading/error in-component, auth model invariato). Raccomandazione: **GO** (basso rischio, valore UX/DX, zero impatto su D-26).
2. **Go/defer/won't sull'Evolutiva** (RSC-fetch sulle sole read-page con cookie-forwarding server→server). Raccomandazione: **GATED su baseline perf reale (verify-first)** — eseguire prima Lighthouse/bundle-analyzer su 2-3 pagine, poi decidere; se GO, solo read-page + rollout a ondate + gate E2E auth.
3. **Conferma scarto della Radicale** (fetch-on-server universale + nuovo session model). Raccomandazione: **WON'T/DEFER** (blast-radius su auth non giustificato dai findings).
4. **Go/defer sulla misura `@next/bundle-analyzer` prima/dopo** per chiudere il verify-first dei QW-D1/D2 già applicati. Raccomandazione: **GO** (a costo quasi-zero, completa l'evidenza).
