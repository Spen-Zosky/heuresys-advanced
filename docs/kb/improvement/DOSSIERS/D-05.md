## TL;DR

Il design-system è **strutturalmente sano** — va detto subito per non gonfiare i finding: **0 raw-hex** su elementi UI (i 138 hex totali sono tutti config chart ECharts/SVG legittimi, F-WS-E-2), **0 `dark:` reali** (le 4 occorrenze sono tutte commenti in `status-pill.tsx` che documentano *perché non usarlo*, F-WS-E-3), **a11y gate `serious=0` incondizionato** già shipped (mobile+desktop, 35 route ×3 personas, 0 violazioni di OGNI severità, F-WS-E-4), **i18n parity perfetta** + script `i18n:check` cablato (F-WS-E-6), **0 `<div/span onClick>`** non-semantici. **Non c'è alcun bug di correttezza né di sicurezza da decidere qui.**

Il lean "evoluzione lib" si scompone in **leve di consolidamento/consistency, non bug**. Due delle tre leve quick-win sono **già chiuse da S993** e non vanno ri-decise (vedi §"Già CHIUSO"). Restano **due decisioni reali** per la Fase-C, entrambe LOW/MEDIUM e accoppiate:

1. **Primitive UI generiche duplicate web↔showcase** (`StatusPill`/`FieldGrid`, byte-identiche, F-WS-E-7) → promuovere in `@heuresys/ui` (tocca il repo sorgente `ux-design-shared` + publish npm) **vs** de-dup interim in-repo **vs** status quo.
2. **Destino di `SystemHealthDashboard.tsx`** (mockup statico, 344 LOC, EN-hardcoded, duplicato, montato su route prod `(authenticated)/system-health`, F-WS-E-2/E-6) → pagina prod reale (i18n + live-data via `SystemHealthLive`) **vs** demo (spostare sotto `/showcase`, toglierla dalla route auth).

## Opzioni

> Le tre opzioni sono **componibili** (Decisione 1 e Decisione 2 sono ortogonali); la triade sotto le mappa su un asse "quanto tocco `@heuresys/ui` / quanto consolido". Pre-condizione comune: i gate dei QW già definiti in `FINDINGS/WS-E.md` §QW-E* (build verdi, `i18n:check` parity, census axe resta `serious=0`).

### Conservativa — "Consolidamento in-repo, zero touch a `@heuresys/ui`"

- **Scope**: nessuna modifica al repo sorgente `ux-design-shared` né publish npm. (a) **De-dup interim** (QW-E5): far sì che `apps/showcase` consumi `status-pill`/`detail-panel`/`SystemHealthDashboard` da **un'unica fonte** — o import da un path condiviso, o estendere `sync-showcase.sh` a copiare anche `components/` (oggi NO) → almeno una sola fonte editabile. (b) **`SystemHealthDashboard`**: i18n delle ~30 stringhe in chiavi `admin`/`shell` IT+EN (QW-E2-residuo) **OPPURE** — più pulito — spostarlo sotto `/showcase` e rimuoverlo dalla route `(authenticated)`, lasciando `SystemHealthLive` come unica system-health di produzione. (c) **QW-E3**: instradare le 4 EmptyState EN di `SystemHealthLive.tsx` via `t(...)` + parity. (d) **QW-E1-coda (opzionale)**: migrare anche i 9 `destructive` residui nelle pagine `showcase/*` a `danger` per uniformità totale (demo-only, basso valore).
- **Impatto**: footprint/DX↑ (una sola fonte per le primitive → niente doppio-fix manuale) · UX/i18n↑ (PLATFORM_ADMIN IT non vede più un dashboard EN, o non vede affatto il mockup) · perf/security **neutri** · governance: **non** chiude la violazione "no reusable UI in apps/web" (le primitive restano nel repo app, solo de-duplicate).
- **Costo**: ~0.5 sessione (tutto in-repo, additivo/meccanico).
- **Rischio**: **basso**. Solo file in-repo; coperto da `next build` 76/76 + `i18n:check` + census axe esistenti. Spostare `SystemHealthDashboard` sotto `/showcase` è il sub-step più "visibile" (cambia cosa vede un PLATFORM_ADMIN su `/system-health` → va confermato che `SystemHealthLive` è il sostituto inteso).
- **Reversibilità**: alta (tutto revertibile a commit-level).
- **Prerequisiti**: decidere se `SystemHealthDashboard` è prod (→i18n) o demo (→sposta a showcase). Le due sono mutuamente esclusive: se si sposta a showcase, l'i18n del mockup decade (QW-E2-residuo non serve).

### Evolutiva — "Promozione delle 2 primitive pure in `@heuresys/ui` + consolidamento system-health" (RACCOMANDATA)

- **Scope**: lavoro nel repo sorgente `ux-design-shared` (Storybook), promozione di **`StatusPill`/`StatusBadge`/`statusTone()`** (da `status-pill.tsx`) e **`FieldGrid`** (da `detail-panel.tsx`) come componenti `@heuresys/ui` → release npm minor (es. `@heuresys/ui@0.1.7`) → bump della dep qui + `pnpm install` → sostituire gli import locali in **entrambe** le app con `import { StatusPill, FieldGrid } from "@heuresys/ui"` → **rimuovere** i 4 file duplicati in-repo. In più: tutta la parte di **consolidamento system-health della Conservativa** (spostare il mockup a showcase O i18n; QW-E3 EmptyState live). `DataTablePanel` resta **escluso** da questo giro (borderline, valutabile in un secondo passo).
- **Impatto**: footprint/DX↑↑ (fonte unica npm-versionata; un fix alla primitiva si propaga via bump, niente mirror manuale) · governance↑↑ (chiude la violazione "no reusable UI in apps/web" — la regola CLAUDE.md torna vera) · qualità↑ (`status-pill`, già template del pattern `dark:`-safe, diventa l'esemplare *condiviso*) · UX/i18n↑ (system-health pulito). Perf/security neutri.
- **Costo**: ~1.5-2 sessioni (lavoro cross-repo `ux-design-shared` + Storybook validation + release npm + bump/consume + rimozione duplicati + system-health). Multi-repo è il costo dominante.
- **Rischio**: **basso-medio**. Le 2 primitive sono presentazionali pure (zero domain, zero `@heuresys/shared` types) → trasferimento meccanico; il rischio è di **processo** (release npm cross-repo, bump corretto, Tailwind `content` glob della lib che già include `@heuresys/ui/dist`, `transpilePackages`). Mitigazione: Storybook valida prima del consumo; gate `next build` 76/76 + `i18n:check` + census axe `serious=0` sulle pagine che usano StatusPill/FieldGrid (detail page, liste).
- **Reversibilità**: media (un bump npm si revoca pinnando la versione precedente; i duplicati rimossi si recuperano da git).
- **Prerequisiti**: working copy `ux-design-shared` allineata; processo publish npm funzionante (è il flusso X18 standard del progetto, già rodato per `@heuresys/ui@0.1.6` su D-27). Decisione 2 (destino mockup) presa.

### Radicale — "Catalogo primitive completo + design-token contract formalizzato"

- **Scope**: oltre alle 2 primitive, promuovere anche **`DataTablePanel`/`EntityTable`** (la state-machine lista loading/error/empty, la più riusabile) in `@heuresys/ui`, e **formalizzare il contratto token** semantico: portare i ~138 hex dei chart (oggi array colore hardcoded in-page, es. `STATUS_COLOR` in `compensation-intelligence`) a leggere i CSS-var token via `getComputedStyle`/theme so che i chart si ri-skinnano su palette-switch; introdurre un set di token-aware chart-color helper in lib. Eventuale audit completo `apps/web/components` per estrarre ogni primitiva genuinamente generica.
- **Impatto**: governance↑↑↑ (zero UI riusabile fuori da `@heuresys/ui`) · coerenza visiva↑ (chart reattivi al palette-switch, oggi statici) · DX↑ su lungo periodo. MA: DX↓ a breve (più superficie lib da mantenere); rischio di **over-extraction** (`DataTablePanel` è borderline-domain — incapsula `DataTableWithCrossHair`, va valutato se è davvero generico o se trascina dipendenze app-specific in lib).
- **Costo**: ~3+ sessioni (cross-repo ampio + refactor chart-color + re-test visivo esteso su tutte le analytics-page).
- **Rischio**: **medio**. Il chart-color-via-token tocca **9 pagine analytics** con re-test visivo su ogni palette; `DataTablePanel` rischia di portare accoppiamento app in lib (anti-pattern: una primitiva lib non deve conoscere il dominio tenant). Reward (chart reattivi al tema) è una **raffinatezza**, non un difetto segnalato — WS-E classifica i 138 hex chart come **legittimi** (F-WS-E-2, "un chart non ha utility token"), quindi il payoff è estetico-opzionale, non una leva di correttezza.
- **Reversibilità**: bassa-media (refactor ampio multi-pagina + nuova superficie lib).
- **Prerequisiti**: Evolutiva completata prima; decisione esplicita che il re-skin chart-on-palette-switch vale l'effort (oggi non è un requisito prodotto noto).

## Raccomandazione motivata

**Evolutiva (GO, ~1.5-2 sessioni, rischio basso-medio) — promozione `StatusPill`+`FieldGrid` in `@heuresys/ui` + consolidamento system-health. Conservativa accettabile come fallback se il budget cross-repo non c'è ora (DEFER della parte npm). Radicale sconsigliata (WON'T/DEFER).**

Razionale evidence-based:

1. **Le leve di *correttezza* sono già incassate da S993** — il doppio-rosso prod (che era un **AA-miss reale**, non un cosmetico: `--destructive` mai registrato → testo invisibile) e i 4 error-state `me/*`/`org-chart` sono chiusi (QW-E1/E2, `0a56d4c`, gate verdi). Ciò che resta è **consolidamento/governance**, non bug. Nessun finding forza un cambio: il design-system è sano.
2. **L'Evolutiva chiude l'unica violazione di governance attiva** (F-WS-E-7: "no reusable UI in apps/web") al costo giusto. Le 2 primitive sono **presentazionali pure** (zero domain, zero dipendenze `@heuresys/shared`) → trasferimento meccanico a basso rischio; il flusso publish-npm cross-repo è **già rodato** (X18 standard, `@heuresys/ui@0.1.6` su D-27). Promuovere `status-pill` — che è *già* il template del pattern `dark:`-safe — lo trasforma da "asset locale duplicato" a "asset condiviso versionato", eliminando il doppio-fix manuale provato dalla mirror-policy di `globals.css:7`.
3. **La Conservativa lascia la violazione aperta**: de-duplica ma le primitive restano in `apps/web` → la regola CLAUDE.md resta violata, e il mirror manuale (anche se ridotto a una fonte) resta un pattern fragile. È un buon **fallback** se Enzo vuole evitare ora il giro cross-repo, ma non è la soluzione "completa" che la dottrina matrice-completa preferisce.
4. **La Radicale è sconsigliata**: `DataTablePanel` rischia over-extraction (borderline-domain), e il chart-color-via-token re-skin è una **raffinatezza estetica** su finding che WS-E ha esplicitamente marcato **legittimi/asset** (F-WS-E-2). Reward opzionale, blast-radius su 9 pagine analytics: il rapporto valore/rischio non è giustificato dai findings.
5. **Su `SystemHealthDashboard` (Decisione 2) la raccomandazione è netta: spostarlo sotto `/showcase` e toglierlo dalla route `(authenticated)`**, NON i18n-izzarlo in-place. Razionale: è un **mockup statico** e esiste già `SystemHealthLive` (query `/v1/*`, RBAC, i18n) come system-health di produzione reale. i18n-izzare 30 stringhe di un mockup che non andrà mai in prod è lavoro sprecato; un PLATFORM_ADMIN su `/system-health` deve vedere dati **live**, non un mock EN. Lo spostamento risolve contemporaneamente i18n (F-WS-E-6), dedup (parte di F-WS-E-7) e live-data-states (F-WS-E-8) per quel file. → **In parallelo, QW-E3** (i18n delle 4 EmptyState di `SystemHealthLive`, F-WS-E-5) va comunque fatto, perché quello è il componente prod reale.

## Cosa decide l'utente

1. **Go/defer/won't sulla promozione `StatusPill`+`FieldGrid` in `@heuresys/ui`** (Evolutiva: lavoro `ux-design-shared` + release npm + bump/consume + rimozione duplicati in-repo). Raccomandazione: **GO** (chiude la violazione governance, basso rischio, flusso npm rodato). Se il budget cross-repo non c'è ora → **fallback Conservativa** (de-dup interim in-repo via `sync-showcase.sh` o import condiviso), con la promozione npm marcata DEFER.
2. **Decisione sul destino di `SystemHealthDashboard.tsx`**: (a) **spostare sotto `/showcase` + rimuovere dalla route `(authenticated)`** [RACCOMANDATO], oppure (b) i18n-izzare in-place come pagina prod. Raccomandazione: **(a)** — è un mockup, `SystemHealthLive` è già il sostituto prod live.
3. **Go/defer su QW-E3** (i18n delle 4 EmptyState EN hardcoded in `SystemHealthLive.tsx:366,397`, F-WS-E-5). Raccomandazione: **GO** (rischio nullo, è il componente prod reale; gate = parity `i18n:check`).
4. **Conferma scarto della Radicale** (`DataTablePanel` in lib + chart-color-via-token). Raccomandazione: **WON'T/DEFER** (over-extraction + raffinatezza estetica non richiesta; i 138 hex chart sono asset legittimi).
5. **Opzionale**: migrare i 9 `destructive` residui nelle pagine `showcase/*` a `danger` per uniformità totale. Raccomandazione: **basso valore (demo-only)** — opzionale, non bloccante.

> Le voci già chiuse da S993 (**QW-E1** 9 pagine prod `destructive`→`danger` / AA-miss invisibile risolto; **QW-E2** 4 error-state `me/*`+`org-chart`) **non** richiedono decisione — sono qui solo come contesto perché Enzo non le ri-apra. **Nota doc-debt** (fix separato, non decisione): `reference_apps_web_color_tokens.md` va aggiornato — la voce "`text-destructive` = invisibile" descriveva il vero stato prod (ora **risolto** da QW-E1), va riscritta come storica; il census i18n SOT va riconciliato (SOT dice 1108×2×7 → reale 1220×2×7 post-S993).
