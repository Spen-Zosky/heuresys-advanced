## Contesto misurato (fatti con numeri/evidenza)

### Cos'è oggi la pipeline di tooling

Il monorepo usa **pnpm come unico task-runner**: i task root sono fan-out lessicali `pnpm -r --filter="@heuresys/*" run <task>` (`package.json:14-17` — `build`/`test`/`lint`/`typecheck`). **Non c'è task-graph** (turbo/nx assente), **non c'è dependency-aware scheduling**, **non c'è affected-only selection**, **non c'è build cache cross-run** oltre allo stato FS warm implicito. Compilazione: `tsup` per il bundle API (`apps/api/tsup.config.ts` — `entry:[src/server.ts]`, `target:node22`, `noExternal:[/^@heuresys\//]` bundla i pkg interni), `tsc` per typecheck, `next build` per web/showcase. Il `clean` esiste già (`package.json:18 → scripts/clean.sh`, QW-2/QW-K1 chiuso S993).

### Il costo reale è coda, non compute (misure CI reali, WS-G)

| Job | Wall-clock | Compute reale | % coda | Fonte |
|---|---|---|---|---|
| typecheck | **14m00s** | 76s (install 12s + tsc ~43s) | ~91% | F-WS-G-14, `gh run view 27448838420 --json jobs` |
| test-integration | **12m42s** | 386s (vitest 353s) | ~50% | F-WS-G-14, `gh run view 27448838430` |
| lint / build-web / showcase | 3m20s / 1m53s / 1m56s | — | — | F-WS-G-14, `gh run list` |

L'insight strutturale (WS-G baseline, riga "Insight chiave"): le durate documentate sono **~80-90% coda** sul **runner unico** (`oracle-vm-default-runner`, **1** registrato — F-WS-G-2) che serializza i 6-7 workflow per push. **La leva velocity #1 è un 2° runner, non micro-ottimizzare un job** — ma il 2° runner ha come **prerequisito** caching dichiarato e portabile.

## Opzioni

### Conservativa — caching dichiarato + copertura task + supply-chain pin (no nuova infra, no task-runner)

**Scope**: chiudere i quick-win di tooling già censiti, restando su `pnpm -r`:
- `cache: pnpm` + `cache-dependency-path: pnpm-lock.yaml` sui 6 setup-node + `actions/cache` per `apps/web/.next/cache` [F-WS-G-15 / QW-G1].
- cache `~/.cache/ms-playwright` per versione + reuse dell'artifact `build-web` invece di ricostruire in playwright-smoke [F-WS-G-18 / QW-G5].
- SHA-pin delle 13 Actions con commento `# vN` (specie peaceiris third-party) [F-WS-G-27 / QW-G2].
- aggiungere `build`(tsup)+`lint`(eslint) ad `apps/agent-gateway` così entra in `pnpm build`/`pnpm lint` [F-WS-A-3 / QW-A2].
- `pino` dev→`dependencies` + drop 2 dead dep [F-WS-A-2 / QW-A1, richiede clean install].

**Impatto**: DX (feedback meno cold sul 2° runner futuro) · robustezza (cache riproducibile/portabile, supply-chain pin) · footprint (copertura completa workspace). **Non tocca il wall-clock 14m** (quello è coda — vedi nota sotto), ma **abilita** la sua soluzione.
**Costo**: ~0.5-1 sessione (meccanico). **Rischio**: BASSO (additivo, gate `pnpm build`+`pnpm typecheck`+suite verdi; `pino` richiede clean install verificato). **Reversibilità**: alta. **Prerequisiti**: nessuno.

> **NB importante**: alcuni di questi (QW-G1/G2/G4/G5 + QW-A2) risultano **già eseguiti nella sessione di hardening CI corrente** (task "CI hardening G1/G2/G4/G5/A2" completato; il `TODO_100X.md` li marca ancora TODO perché precede l'esecuzione). Da **riconciliare con lo stato live** prima di ridecidere — vedi §"Già chiuso".

### Evolutiva — task-runner affected-only (turbo o nx) + 2° runner

**Scope**: introdurre un **task-graph monorepo** (la `lean` misurata):
- adottare **turbo** (più leggero, meno opinionato) o **nx**: `turbo.json` con pipeline `build`/`typecheck`/`lint`/`test` + `dependsOn` derivato dal grafo workspace reale (shared→api→web, già pulito F-WS-A-4) + cache locale/remota.
- CI gira **affected-only** rispetto a `origin/main`: un cambio in `apps/web` non ri-typechecka api/shared inalterati [F-WS-G-17]. Taglia compute **e** pressione-coda.
- in tandem: **2° runner** (ephemeral on-VM o off-prod) che parallelizza lint/i18n/typecheck/build [F-WS-G-14] — la cache dichiarata della Conservativa è il suo **prerequisito** (cold install altrimenti).
- caching turbo riusa gli output (`.next`, `dist`, `tsbuildinfo`) tra run invece del FS warm implicito.

**Impatto**: DX **alto** (i 14m queue-bound collassano verso il compute reale ~76s quando il fan-out non serializza più + affected salta i workspace inalterati) · robustezza (cache esplicita riproducibile). Per **vitest** il guadagno è **limitato**: resta serial by-design (DB condiviso, F-WS-G-16) finché non si separa il DB CI (quello è **D-08**, non qui) — turbo può però *skippare* l'intero job test quando `apps/api` è inalterato.
**Costo**: ~1.5-2.5 sessioni (turbo.json + ricablare i workflow su `turbo run --filter=...[origin/main]` + tuning cache + il 2° runner se incluso). **Rischio**: MEDIO (cambio del runner di task tocca tutti i workflow + il flusso locale `pnpm dev`; mitigato dal grafo pulito e da gate per-workflow). **Reversibilità**: media (turbo è additivo sopra pnpm — gli script per-package restano, si rimuove `turbo.json` per tornare a `pnpm -r`). **Prerequisiti**: caching dichiarato (Conservativa) + decisione sul 2° runner (overlap con **D-08** F-WS-G-2).

### Radicale — riarchitettura build: bundle/compiler swap + monorepo orchestrator full + remote cache

**Scope**: ripensare la toolchain di build oltre il task-graph:
- valutare lo swap del compilatore: `tsup`(esbuild) → mantenere, **oppure** `tsc` build-mode con **project references** (`composite:true` + `tsc -b`) per typecheck incrementale nativo cross-workspace (elimina il re-typecheck full senza un orchestrator esterno), **oppure** un bundler unico (vite/rolldown) per api+web.
- **remote build cache** (turbo remote cache self-hosted / nx cloud) condivisa tra Windows-dev, Mac, VM, linux-pc twin — un build/typecheck già fatto su una macchina non si rifà sulle altre.
- monorepo orchestrator full (nx con plugin generator) che assorbe anche il **codegen del module-pattern** (R14 / D-01: routes uniformi `actor()`+requirePermission+verifyCsrf ×75 = ~50-60% scaffolding) → un task-runner che genera **e** builda i moduli.

**Impatto**: DX massimo a regime (incrementale nativo + cache distribuita cross-host) + convergenza con D-01 (codegen). Ma **alto blast-radius**: tocca `tsup.config`/`vitest`/`next` simultaneamente, il vincolo `noExternal:[/^@heuresys\//]` (boot prod), il flusso E2E-locale `next dev`, e i 4 host di sviluppo.
**Costo**: ≥3-4 sessioni + iterazione di stabilizzazione. **Rischio**: ALTO (riarchitettura di build su un prodotto GA con deploy `vm-deploy.sh` che assume `node dist/server.js`; ogni regressione di bundle rompe il boot prod). **Reversibilità**: bassa una volta migrati i compilatori. **Prerequisiti**: Evolutiva consolidata + D-01 (codegen) deciso + D-08 (infra runner/DB CI) per sfruttare davvero la remote cache.

## Raccomandazione motivata

**Conservativa ora (per la parte non già eseguita), Evolutiva come prossimo incremento mirato, Radicale → DEFER.**

Motivazione evidence-based:

1. **Il problema #1 è la coda del runner unico (~80-90% del wall-clock), non il compute** (F-WS-G-14 baseline). Nessuna ottimizzazione di compilatore o di task-graph lo risolve da sola: serve la **cache dichiarata** (Conservativa, prerequisito) + il **2° runner**. Quindi la sequenza obbligata parte dalla Conservativa, non dalla Radicale.
2. **L'affected-only (la `lean` misurata) è reale e ben fondato**: il grafo dipendenze del monorepo è già pulito (0 cicli, `shared` leaf — F-WS-A-4), quindi turbo può fidarsi del `dependsOn` derivato senza bonifiche preliminari. È il singolo cambio col miglior rapporto leva/rischio **dopo** la cache — taglia il re-typecheck full su ogni 1-liner (F-WS-G-17) e permette di *skippare* interi job (incluso il pesante test serial) quando il workspace è inalterato, aggirando indirettamente il soffitto vitest (F-WS-G-16) senza dover ancora separare il DB CI (che è D-08).
3. **vitest resta il collo strutturale ma non è risolvibile in D-06**: il suo parallelismo è bloccato dal **DB live condiviso** (F-WS-G-16/F-WS-G-3) — è materiale **D-08** (DB CI separato/schema-per-shard) + **D-B** (test-pyramid). D-06 può solo *evitare di rieseguirlo* via affected. Non vendere a Enzo un guadagno vitest da turbo: sarebbe over-promise.
4. **La Radicale (compiler swap + remote cache + codegen) è prematura**: il blast-radius su un GA con boot prod dipendente da `tsup noExternal` è alto e i suoi prerequisiti (D-01 codegen, D-08 infra) non sono ancora decisi. Va tenuta come nord, non eseguita ora.

**Sequenza proposta**: (a) verificare lo stato live dei QW-G/QW-A già eseguiti → chiudere i residui Conservativi; (b) se Enzo vuole la leva velocity, fase Evolutiva = `turbo` affected-only **insieme** alla decisione 2°-runner di D-08 (sono accoppiati: la cache portabile serve a entrambi). La Conservativa è low-risk/additiva e si può eseguire come CLASS-A su go; l'Evolutiva è una scelta architetturale → resta decisione Enzo.
