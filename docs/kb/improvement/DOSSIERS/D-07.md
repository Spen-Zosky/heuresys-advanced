## TL;DR

La catena di **127 migration** (`000001..000128`, gap `000035` cosmetico documentato) è **strutturalmente sana e a costo di deploy nullo**, non un debito. Il deploy PROD non riapplica nulla di già applicato: `db/scripts/migrate-if-pending.sh:36-55` è **sha-gated** (confronta `file_name:sha256` col ledger `sys.sys_schema_migrations`) → a deploy reale gira **solo il pending**, O(pending). L'intera catena è sub-secondo per file (top duration osservate 53-99 ms). L'unico "costo" misurato è **DX/footprint**: 127 file da scorrere quando si cerca lo storico di una tabella — impatto basso, zero impatto su perf o robustezza.

Lo squash è quindi una decisione **discrezionale, low-priority**, non un fix. La raccomandazione (vedi §Raccomandazione) è **CONSERVATIVA — non squashare ora**: ogni opzione di consolidamento o paga un costo di re-verifica (rompe la property *twice-run-empty-diff* provata) o distrugge lo storico `sha256` di audit, a fronte di un beneficio marginale. Niente in F-WS-C-7/8 è urgente né bloccante; **nessun item D-07 è stato chiuso da S993** (è un dossier puro di scelta, non aveva quick-win associati).

## Contesto misurato (fatti, non impressioni)

### Lo stato attuale è un ASSET (F-WS-C-8), non un problema

Il ledger `sys.sys_schema_migrations` è il pattern corretto e va **preservato**, non smontato:

- Colonne: `migration_id serial PK`, `file_name UNIQUE`, `sha256 char(64) NOT NULL`, `applied_at timestamptz`, `applied_by`, `duration_ms`; indici `applied_at_idx` / `file_name_uq`.
- Il wrapper di deploy `db/scripts/migrate-if-pending.sh:36-55` confronta `file_name:sha256` contro il ledger → rileva **sia file nuovi sia drift di contenuto** di un file già applicato (sha mismatch ⇒ pending ⇒ riapplica). Override `DB_MIGRATE=force|skip|auto`.
- Il solo `db/scripts/migrate.sh:40-64` **ri-applica OGNI file ad ogni invocazione** (nessuna skip-logic — l'INSERT nel ledger è un `ON CONFLICT DO UPDATE` di audit, non un gate). Questo è **intenzionale** per dev/reset; il gating per PROD vive nel wrapper. Il `migration_id` seriale a **7445** prova le molte ri-applicazioni full storiche (dev/test), **non** un costo di deploy.

### Il costo misurato (F-WS-C-7) — basso, DX-only

| Metrica | Valore reale | Fonte |
|---|---|---|
| File migration | **127** (`000001..000128`, gap `000035` cosmetico) | `ls db/migrations/*.sql \| wc -l` = 127 |
| Righe ledger | **127** distinte (UNIQUE `file_name`; sha256+duration) | `SELECT count(*) FROM sys.sys_schema_migrations` |
| `migration_id` serial | **@ 7445** (ri-apply storiche dev/test, non deploy) | ledger PK |
| Idempotenza | **68** `IF NOT EXISTS` · **71** `ON CONFLICT` · **0** `DO $$` | `grep -rl … db/migrations/*.sql` |
| File senza guard esplicito | **6** — naturalmente re-runnable | vedi sotto |
| Durata catena | sub-secondo/file (53-99 ms top) | `duration_ms` nel ledger |
| Deploy migrate | `migrate-if-pending.sh` sha-gated → **O(pending)** | `db/scripts/migrate{,-if-pending}.sh` |
| Property | **twice-run-empty-diff provata** (ADR/registro) | — |

I **6** file senza guard esplicito — `000032` (relax-CHECK), `000038`/`000041` (nullable-FK), `000044`/`000056` (reclassify), `000094` (insights-collapse) — sono **naturalmente re-runnable** (ALTER DROP/ADD CONSTRAINT, DELETE-collapse → 2° run = 0 righe). Non sono un buco di idempotenza.

**Insight chiave**: la catena non costa nulla a runtime (deploy = solo pending) e nulla a robustezza (idempotente + sha-gated + storico audit). Il solo attrito è cognitivo/DX: 127 file in `db/migrations/`. Il valore di qualunque squash si misura *solo* contro quell'attrito.

## Opzioni

### Conservativa — Lasciare la catena com'è (no-op)

- **Scope**: nessuna modifica. Si continua ad aggiungere file sequenziali idempotenti col pattern esistente. Si documenta (eventualmente in `CLAUDE.md` §"Database migrations" o nel `DEBT_REGISTER.md` come WON'T-DO esplicito) che lo squash è stato valutato e respinto in Fase-C, così non riemerge.
- **Impatto**: perf = 0 (deploy già O(pending)); robustezza = 0 (property idempotente preservata); DX = invariata (127 file restano, ma sono ordinati e ledger-tracciati); footprint = 0.
- **Costo**: **0 sessioni** (al più 1 riga di documentazione, CLASS-A).
- **Rischio**: nullo.
- **Reversibilità**: totale (si può sempre squashare in futuro).
- **Prerequisiti**: nessuno.

### Evolutiva — Baseline-snapshot additivo + archivio dei 1xx storici

- **Scope**: generare un `000000_baseline.sql` = `pg_dump --schema-only` dello schema GA corrente (tabelle/indici/constraint/view), poi **archiviare** i file storici `000001..000128` in `db/migrations/_archive/` **senza** cancellarne le righe dal ledger (preserva lo `sha256` di audit). I nuovi ambienti partono dal baseline + i soli delta post-GA; gli ambienti esistenti restano sul ledger storico.
- **Impatto**: DX migliorata per chi parte da zero (1 file di schema invece di 127); perf/robustezza invariate. Ma introduce **dualità**: schema-init via baseline per i nuovi DB vs catena-completa per gli esistenti.
- **Costo**: **~1 sessione** (generazione snapshot + riorganizzazione + ri-prova della property).
- **Rischio**: **MEDIO** — **rompe la property twice-run-empty-diff** provata sulla catena attuale; il baseline-snapshot va re-provato per idempotenza e parità con la catena lineare (un `pg_dump` schema-only può divergere da ciò che producono i 127 file per ordine/dettagli di default/owner). Rischio di skew tra "ricostruito da baseline" e "ricostruito da catena".
- **Reversibilità**: alta (l'archivio non cancella nulla; si può tornare alla catena lineare ripristinando i file).
- **Prerequisiti**: re-derivare e committare la prova di empty-diff per il nuovo path baseline; allineare `migrate.sh`/`migrate-if-pending.sh` al fatto che `000000` è uno stato-zero, non un delta.

### Radicale — Squash distruttivo: collassare i 127 file in pochi file consolidati

- **Scope**: riscrivere lo storico delle migration fondendo i 127 file in N file consolidati (es. uno per dominio), eliminando i file intermedi e **riazzerando il ledger**.
- **Impatto**: DX nominalmente più pulita; ma **perde lo storico `sha256`** (audit del drift-detection di `migrate-if-pending.sh`), perde la tracciabilità per-tabella di *quando/perché* è cambiata una colonna, e richiede di re-baselineare ogni ambiente esistente (PROD VM, twin linux-pc, dev locali, CI) manualmente.
- **Costo**: **~1-2 sessioni** + coordinamento multi-host (re-stamp del ledger su ogni ambiente).
- **Rischio**: **ALTO** — distrugge l'asset di audit (F-WS-C-8), rompe il drift-detection sha-gated, e ogni ambiente esistente va re-allineato a mano (rischio di stato inconsistente tra VM/twin/dev). Irreversibile sul lato storico (lo `sha256` perso non si ricostruisce).
- **Reversibilità**: bassa (storico ledger non recuperabile).
- **Prerequisiti**: freeze coordinato di tutti gli ambienti; re-stamp manuale del ledger ovunque; ri-prova completa.

## Raccomandazione motivata

**CONSERVATIVA — non squashare ora, e formalizzarlo come WON'T-DO valutato.**

Tre fatti misurati convergono:

1. **Il costo che lo squash eliminerebbe non esiste a runtime.** Il deploy è già O(pending) via sha-gate (`migrate-if-pending.sh:36-55`); la catena è sub-secondo/file; 0 impatto su perf/robustezza (F-WS-C-7/8). Il solo costo è leggere 127 file — DX, basso, e mitigato dall'ordinamento sequenziale + ledger interrogabile.
2. **Ogni alternativa paga di più di quanto rende.** L'Evolutiva rompe la *twice-run-empty-diff* provata e introduce dualità init (rischio MEDIO, ~1 sessione per re-provare). La Radicale distrugge lo `sha256`-audit (l'ASSET F-WS-C-8) e richiede re-stamp multi-host (rischio ALTO, irreversibile). Nessuna delle due compra perf o robustezza — solo cosmetica.
3. **L'asset va protetto, non smontato.** Il ledger sha256 + drift-detection è uno dei punti di forza della persistenza (`v_reconciliation_status` 148 POPULATED, 0 dead-schema, FK integri, RD-08/09 rispettati — gruppo ASSET WS-C). Un dossier non deve regredire un asset per ridurre un attrito DX trascurabile.

La nota del lean S-100X-0 ("baseline GA + delta separati") resta una **traiettoria futura legittima** se e quando il count infastidisce davvero: in quel caso la via è l'**Evolutiva** (baseline-snapshot additivo che preserva il ledger), **mai** la Radicale distruttiva. Ma oggi non c'è un trigger che la giustifichi.

**Soglia di rivalutazione suggerita**: riconsiderare l'Evolutiva solo se (a) il count supera nettamente i ~200 file *e* (b) emerge un costo concreto (es. un nuovo ambiente che deve essere bootstrappato spesso da zero e per cui la catena diventa un attrito operativo misurabile, non percepito). Fino ad allora: status quo.
