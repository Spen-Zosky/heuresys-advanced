## Contesto misurato (fatti con numeri/evidenza)

### Topologia attuale (la radice di tutto)

Il repo è **PUBBLICO** (`gh repo view --json visibility` → `PUBLIC`) e ha **un solo runner CI** (`gh api .../actions/runners` → **1**: `oracle-vm-default-runner`, online, ARM64) che **è la VM PROD** (`oracle-vm-default`: web :3013, api :8013, PostgreSQL :5432 — `deploy/README.md:149,153`). 7 degli 8 workflow girano `runs-on: [self-hosted, oci-vm]`, come OS user `ubuntu` = **lo stesso user che possiede i servizi prod** (`heuresys-advanced-api.service:11 User=ubuntu`) con accesso trusted a `psql -h localhost -p 5432` sul **DB prod** (`test-integration.yml:67-69`, `POSTGRES_DB=heuresys_advanced`). Quindi CI-compute, secret-on-host, e runtime PROD condividono lo stesso kernel, lo stesso user e lo stesso DB.

Da questa singola topologia discendono tre classi di problema, tutte misurate in WS-G:

**1. Sicurezza (era il CRITICAL del programma).** `F-WS-G-1` (CRITICAL): 7/8 workflow self-hosted avevano trigger `pull_request: branches:[main]` senza actor/owner gate → una **fork-PR** che tocca `apps/api/**` eseguiva vitest/build **attacker-controlled sul box di produzione** con accesso a secret prod-adiacenti (`F-WS-G-5`: `/etc/heuresys-runner.env` letto come shell-var) e a `localhost:5432`. Il runner è long-lived/non-ephemeral (`F-WS-G-6`: `_work` + pnpm-store + secret persistono tra run e tra PR), e le Actions sono pinnate a **tag mobili** (`F-WS-G-27`: 0/13 a SHA → tag-mutation su un runner secret-bearing). Modello solo-dev trunk-based **direct-to-main** su repo pubblico senza branch protection (`F-WS-G-25`: 242 commit / 0 merge dal v1.0.0).

**2. Robustezza CI (SPOF + accoppiamento DB).** `F-WS-G-2` (HIGH): 1 runner, 0 ridondanza → VM giù = **CI e PROD cadono insieme** (il jitter OCI free-tier S980, 4 boot falliti, ne è la demo live). `F-WS-G-3` (HIGH): la CI gira contro il **LIVE PROD DB** — 901 it-block + `pnpm db:seed-test-admin` mutano lo stesso DB che serve PROD a ogni push/PR. `F-WS-G-4` (HIGH): CI heavy (`next build`, chromium-install, 901-it) **senza alcun limite** (`grep container:|cgroup|MemoryMax|CPUQuota` → 0 hit) sullo stesso kernel di prod → uno spike RAM sull'ARM free-tier degrada PROD.

**3. Robustezza deploy (0 rollback).** `F-WS-G-8` (HIGH): `vm-deploy.sh:44-46` fa `fetch; reset --hard origin/$BRANCH` poi build lineare → restart, **nessuna sha catturata prima del reset, nessun release-dir/symlink, nessun auto-revert** (`grep rollback|last.good|previous.sha` → 0 hit in vm-deploy.sh). `F-WS-G-9` (HIGH): la health probe (`vm-deploy.sh:140-147`) su `/readyz` fail fa solo `echo FAILED` — **osserva ma non agisce**, e il restart è già avvenuto → **il build rotto è già LIVE** quando la probe gira. `F-WS-G-10` (HIGH): **nessuno `pg_dump` pre-migrate** (`vm-deploy.sh:83-84` chiama `migrate-if-pending.sh` senza snapshot) + **nessun backup schedulato** (cross-ref R5) = **zero restore-point** sull'unico DB prod irrimpiazzabile; le migration sono forward-only (`F-WS-G-11`, glob `db/migrations/*down*` → 0). Recovery 100% manuale, nessun runbook (`F-WS-G-12`). E `align-clones.sh --auto-deploy` a session-close può propagare un prod rotto in silenzio (`F-WS-G-13`).

### Release & gating (la CI è advisory, mai gating)

`F-WS-G-21` (HIGH): `main` ha **0 required-status-checks e 0 required-PR** (`gh api .../branches/main/protection` → 404; ruleset `main-protection-tier1` ha solo `deletion`+`non_fast_forward`). I workflow triggano su `push:` → la CI gira **dopo** che il commit è già su main. `F-WS-G-22` (HIGH): PROD fa `reset --hard origin/main` HEAD, **non un tag** → un commit direct-to-main può essere deployato dal prossimo `vm-deploy.sh` **prima che la sua CI finisca**. `F-WS-G-24` (MEDIUM): semver drift — tutti i package.json a `1.0.0` su 242 commit post-GA (incl. feature + un major bump). Release 100% manuali (`F-WS-G-23`).

### Asset strutturali da NON regredire (WS-G "Asset confermati")

- **NO auto-deploy-on-push** (`workflows-overview.md:19`): **nessun workflow invoca `vm-deploy.sh`** (`grep uses: → 0`). Il deploy app gira solo via `bash scripts/vm-deploy.sh` su SSH di Enzo. **Questo è il controllo strutturale che impedisce a R01+R02 di essere un path CI-RCE-to-prod automatico** → R02 è errore-operatore/no-rollback, **non** RCE. **Il più importante da preservare in ogni evoluzione.**
- **Secret hygiene**: 0 secret reali nel tree (`git ls-files | grep -iE '\.pem$|\.key$|\.secrets/'` → none), 0 secret inlined in YAML (solo `GITHUB_TOKEN`), EnvironmentFile mode 600 root-owned, LOG_REDACT_PATHS live, PEM via stdin.
- **Hardening deploy già presente**: self-modify-buffer re-exec (`vm-deploy.sh:49-58`), Node-ABI clean reinstall (64-77), clean shared build (D-17), frozen-lockfile fail-loud (72-76), migrate-if-pending sha256 ledger.
- **Branch**: force-push + deletion protection ATTIVE; tag annotati semver-clean + 6 GitHub Releases; CI gira su push **e** PR (la coverage esiste — basta abilitare i required-checks).

## Opzioni

### Conservativa — chiudere SPOF/rollback/gating senza nuova infra (tutto on-VM, additivo)

**Scope** (resta sull'unica VM, nessun box nuovo):
- **DB/schema CI separato** [F-WS-G-3]: i 2 gate DB (`test-integration`, `playwright-smoke`) puntano a un DB/schema non-prod sulla stessa VM (es. `heuresys_ci`) invece di `heuresys_advanced` → rompe il data-coupling CI↔PROD.
- **systemd cgroup-slice** sull'unit del runner [F-WS-G-4]: `MemoryMax`/`CPUQuota` per impedire che un `next build`/chromium-install spike degradi PROD.
- **`--ephemeral` runner** [F-WS-G-6]: teardown per-job → un job non avvelena il workspace del successivo; secret non persistono tra PR.
- **Rollback scriptato** [F-WS-G-8/9/12]: `LAST_GOOD=$(git rev-parse HEAD)` catturato **prima** del reset + `vm-rollback.sh <sha>` + probe **come gate** (non-2xx → trigger rollback + `exit` non-zero così align-clones vede rosso) + runbook in `deploy/README.md`.
- **`pg_dump -Fc` timestamped come step-0 del deploy** [F-WS-G-10] (solo se migration pending) + stampa del restore one-liner → trasforma forward-only (F-WS-G-11) in sopravvivibile.
- **`required_status_checks` sul ruleset esistente** [F-WS-G-21] (typecheck/lint/test/build/i18n/playwright) + **deploy-gate** su CI-verde [F-WS-G-22]: `vm-deploy.sh` rifiuta sha senza `gh run list --commit <sha> --conclusion success`. Gestire il caso `defer-major` [F-WS-G-26] (shim skip-to-success).
- **Gate fork-PR** [F-WS-G-1] — **GIÀ FATTO S988**, vedi §"Già chiuso".

**Impatto**: sicurezza (DB-coupling rotto, runner ephemeral) · robustezza (restore-point reale, rollback in un comando, CI finalmente gating) · DX (deploy-gate evita il deploy di un commit con CI in volo). **Non risolve la coda 14m** (serve il 2° runner — Evolutiva) né lo SPOF runner==PROD.
**Costo**: ~1-1.5 sessioni (script + ruleset + 1 unit systemd). **Rischio**: BASSO-MEDIO (additivo; il rischio reale è il `required_status_checks` su runner unico — vedi nota F-WS-G-2: un check required che hang il runner-PROD **bloccherebbe tutti i merge** → va deciso *quali* check sono mandatory). **Reversibilità**: alta. **Prerequisiti**: nessuno per la maggior parte; il required-check va deciso con cautela finché il runner è SPOF.

### Evolutiva — runner OFF-PROD + deploy atomico release-dir + affected/cache (chiude SPOF alla radice)

**Scope** (la direzione "alta-leva" della lean): sposta il **compute CI fuori dal box prod**.
- **Runner off-prod** [F-WS-G-2/3/4/5/7]: box/container separato (il twin linux-pc è già x86_64 LAN, candidato naturale — oggi è clone isolato, non un gate); i 2 gate DB raggiungono un **DB non-prod** via tunnel. Chiude in un colpo **SPOF-redundancy + resource-contention + fork-PR exposure + secret-on-prod** (la direzione già identificata e mai eretta — F-WS-G-7).
- **2° runner / parallelismo** [F-WS-G-14]: il fan-out non serializza più → i 14m queue-bound collassano verso il compute reale (~76s typecheck).
- **Caching dichiarato + affected-only** [F-WS-G-15/17] (overlap **D-06**): prerequisito del 2° runner (altrimenti cold install ~3GB); affected salta i workspace inalterati.
- **Deploy atomico** [F-WS-G-8/9]: `releases/`+`current`→release-N symlink swap atomico (ritieni N-1) + **auto-revert su probe-fail** invece del reset-in-place.
- **SBOM + dependency-review** [F-WS-G-28]: `anchore/sbom-action` come artifact CI + `actions/dependency-review-action` su PR.

**Impatto**: sicurezza **alta** (la superficie self-hosted-on-prod sparisce — anche se la fork-PR è già gated, l'off-prod elimina la classe intera) · robustezza alta (CI e PROD disaccoppiati, deploy atomico con N-1) · DX alta (queue-bound risolto). 
**Costo**: ~2-3 sessioni (provisioning runner off-prod + tunnel DB non-prod + ricablaggio `runs-on` + release-dir su vm-deploy). **Rischio**: MEDIO (nuova infra da mantenere; il release-dir cambia la meccanica deploy di un GA — va testato sul twin prima). **Reversibilità**: media (il runner off-prod si rimuove ri-registrando on-VM; il release-dir è un cambio di vm-deploy reversibile). **Prerequisiti**: caching dichiarato (D-06 Conservativa) + decisione su *dove* sta il runner off-prod (linux-pc vs nuovo box).

### Radicale — GitHub-hosted runner + managed/replica DB CI + blue-green deploy

**Scope**: elimina **tutta** la superficie self-hosted.
- **GH-hosted runner** (ubuntu-latest, come già showcase.yml) + **replica DB non-prod** raggiunta via tunnel/managed-CI → zero compute attacker-controllable su qualsiasi box di Enzo. Il costo storico (pnpm-store cold ~3GB ad ogni run, ragione originale del self-hosting) è ora **pesabile contro** la sicurezza, con caching dichiarato che lo mitiga.
- **blue-green / artifact immutabile** per il deploy app: build un artifact, swap di traffico, rollback = swap inverso istantaneo → elimina sia il reset-in-place sia la finestra "build rotto già LIVE".
- **release automation** [F-WS-G-23/24]: `release.yml` tag-triggered (build + artifact + notes + deploy gated) + changesets per il semver bump-on-ship.

**Impatto**: massimo a regime (0 self-hosted surface, deploy reversibile istantaneo, release auditabili). 
**Costo**: ≥3-4 sessioni + stabilizzazione (managed DB CI o replica + blue-green su `vm-deploy` che oggi assume `node dist/server.js` in-place). **Rischio**: ALTO (riarchitettura deploy su GA; il GH-hosted ARM/x86 cambia toolchain vs ARM64-VM; managed DB CI = costo/setup ricorrente). **Reversibilità**: bassa una volta migrati deploy+DB CI. **Prerequisiti**: Evolutiva consolidata; decisione costo managed-CI/DB (CLASS-B infra/costo — registrata, non decisa autonomamente).

## Raccomandazione motivata

**Conservativa ORA (residuo post-S988), Evolutiva come prossimo incremento mirato (runner off-prod + deploy atomico), Radicale → DEFER.**

Motivazione evidence-based:

1. **Il CRITICAL è già chiuso.** `F-WS-G-1` (fork-PR ACE) è **MITIGATO S988** (`7177dda`, fork-guard job-level su tutti i 7 workflow → una fork-PR è skippata dal controller GitHub **prima** del checkout sul runner). Quindi D-08 **non è più un'emergenza security-priority**: è tornato un dossier di robustezza con un residuo security defense-in-depth. Enzo **non deve ri-decidere** il vettore F-1 (vedi §"Già chiuso").

2. **Il residuo a più alto valore/costo è il `pg_dump` pre-deploy** (`F-WS-G-10`). Il DB prod è l'asset irrimpiazzabile, è **uno solo** (lo stesso raggiunto da Windows via tunnel :5433), e oggi una migration parziale/fallita **non ha restore-point** (forward-only, 0 backup schedulato — cross-ref R5). È ~1-2h, additivo, zero blast-radius. È il singolo hardening da fare per primo.

3. **La sequenza è obbligata: prima rollback/gating on-VM (Conservativa), poi off-prod (Evolutiva).** Il `LAST_GOOD`+`vm-rollback.sh`+probe-as-gate (F-8/9/12) e il deploy-gate su CI-verde (F-22) sono additivi e low-risk, e rendono *sopravvivibile* l'attuale topologia mentre si pianifica l'off-prod. Il `required_status_checks` (F-21) va però introdotto **con cautela**: finché il runner è SPOF==PROD, un check mandatory che hang il runner blocca **tutti** i merge → meglio renderlo required **dopo** il 2° runner, o partire con un sottoinsieme (typecheck/lint, non i gate DB lunghi).

4. **L'off-prod (Evolutiva) è la cura strutturale, non un nice-to-have.** Chiude in un colpo SPOF (F-2) + DB-coupling (F-3) + resource-contention (F-4) + secret-on-prod (F-5/6) — la direzione "runner isolato/off-prod" è **già stata identificata e respinta solo nella variante desktop** (B-30 WON'T-DO, F-WS-G-7), mai eretta. Il twin linux-pc x86_64 è il candidato naturale. È accoppiata a **D-06** (caching/affected) e va decisa insieme.

5. **La Radicale (GH-hosted + managed DB CI + blue-green) è prematura.** Il blast-radius su un GA con `vm-deploy.sh` che assume `node dist/server.js` in-place è alto, e introduce costo ricorrente (managed-CI/DB). Va tenuta come nord — la si valuta solo se l'off-prod sulla VM/twin si rivela insufficiente. **Asset da non perdere mai**: la regola "NO auto-deploy-on-push" (deploy solo manuale-SSH) va preservata in *ogni* opzione — è ciò che ha contenuto F-1+R02 a non-RCE.

**Sequenza proposta**: (a) `pg_dump` pre-deploy + `LAST_GOOD`/`vm-rollback.sh` + probe-as-gate + runbook [Conservativa core, ~1 sessione, CLASS-A su go]; (b) DB/schema CI separato + cgroup-slice + `--ephemeral` [Conservativa security/robustezza, ~0.5 sessione]; (c) deploy-gate su CI-verde + required-checks *minimi* [Conservativa gating, va con (e)]; (d) **decisione Enzo**: runner off-prod su linux-pc → sblocca required-checks pieni + parallelismo (Evolutiva, accoppiata D-06).

## Cosa decide l'utente

1. **`pg_dump` pre-deploy + rollback scriptato** (F-10/8/9/12 — `pg_dump -Fc` step-0 + `LAST_GOOD` + `vm-rollback.sh` + probe-as-gate + runbook): il singolo hardening più alto-valore/costo dato che il DB prod è irrimpiazzabile e oggi ha **zero restore-point**. Go ora? *(low-risk, additivo, ~1 sessione, CLASS-A)*
2. **DB/schema CI separato + cgroup-slice + `--ephemeral`** (F-3/4/6): rompe il data-coupling CI↔PROD e i secret-persistence tra PR, restando sull'unica VM. Go ora / con l'off-prod / defer?
3. **Deploy-gate su CI-verde + `required_status_checks`** (F-22/21): la CI diventa gating invece di advisory. **Trade-off da decidere**: required-checks su runner SPOF==PROD può bloccare tutti i merge se il runner hang → quali check mandatory (solo typecheck/lint) e quando (prima/dopo il 2° runner)?
4. **Runner OFF-PROD** (Evolutiva, F-2/3/4/5/7): chiude SPOF + contention + secret-on-prod alla radice. **Dove**: twin **linux-pc** x86_64 (già LAN, candidato) o nuovo box? Accoppiato a **D-06** (caching/affected). Go / dopo la Conservativa / defer?
5. **Deploy atomico release-dir + auto-revert** (F-8/9 Evolutiva) vs **status quo reset-in-place**: introdurre `releases/`+`current` symlink (ritieni N-1)? Va testato sul twin prima (GA, blast-radius su deploy).
6. **Radicale** (GH-hosted + managed/replica DB CI + blue-green): tenere come nord o escludere dallo scope 100X? *(CLASS-B infra/costo — registrata, decisione Enzo)*

*Vincolo invariante da preservare in ogni opzione: **NO auto-deploy-on-push** (deploy solo manuale-SSH) — è il controllo che ha tenuto F-1+R02 fuori dal percorso CI-RCE-to-prod. Nessun contratto pubblico (`/v1/*`, schema `sys.*`, Zod) né invariante I1-I14 è toccato da D-08 (è infra CI/deploy). La decisione go/defer/won't per-opzione è di **Enzo**.*
